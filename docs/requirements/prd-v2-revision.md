## 1. 产品概述

### 1.1 背景与问题

部门有大量已应用于生产线的三维模型、二维图纸、CAD 源文件、仿真文件，以及配套的规范、作业指导书、调试验收资料。它们主要存在工程师个人电脑里，带来几个具体问题：

- **找不到**：资料分散在各人手里，别人不知道有没有、在谁那。
- **认不出**：文件命名、目录、分类各有一套，查找靠个人经验。
- **会丢失**：人一调岗或离职，资料就难找甚至失传。
- **存重复**：同一份资料多人保存，版本还未必一致。
- **不规范**：旧系统图纸缺基地、拉线、工序段等结构化信息；什么字段必填、编号怎么编、文件怎么命名、验收要达到什么门槛，没有统一说法。
- **收不进来**：散落在员工手里的资料没有组织化的征集入口，治理只能处理"已经在库里"的问题数据。
- **用不起来**：资料治理完成后缺乏 AI 数据交付通道，无法沉淀为企业知识资产。

### 1.2 产品目标

1. 把散落的图纸模型集中保存，形成部门仿真数模资产，统一维度（平台、蓝本、基地、拉线）查找。
2. 用批量上传、自动填充降低工程师录入成本；支持预览、下载、收藏、评论，方便日常使用。
3. 建立**数据标准体系**：把业务规矩变成系统可执行的规则，自动检查、统一验收尺度。
4. 建立**资料征集与责任体系**：散落文件通过"任务分发 → 提交 → 可追溯"进入公司资产流程，责任不因人员变动丢失。
5. 完成 **AI 数据交付**：已标准化、权限明确、质量达标的资产可加工为 RAG 语料。
6. 历史数据平滑迁移：旧系统数据原样保留、可追溯治理，不因切换丢失。

### 1.3 用户与角色

| 角色 | 主要职责 |
| --- | --- |
| 普通员工 | 按征集任务提交文件；查找、预览、下载、收藏、评论授权范围内的资料 |
| 资产责任人 | 上传资产，确认文件归组、资产性质、功能、适用范围，执行业务确认 |
| 文档维护者 | 创建和维护知识文档，发布新版本，设置适用范围并关联数模资产 |
| 标准评审人 | 评审数据标准（由内容管理员配置，至少 1 位，可多名） |
| 内容管理员 | 编制与发布标准、维护字典与映射、组织治理任务与资料征集、质量验收、运营复盘 |
| 部门管理者 | 查看运营指标、月度复盘、推动整改与考核 |
| 系统管理员 | 管理用户权限、数据范围和基础字典 |

### 1.4 核心场景

1. **工程师上传新资料**：选文件夹上传，确认哪些文件属于同一份资料，批量填基地、拉线和专业类别，提交后立即可用。
2. **用户查找图纸**：按基地、拉线、平台、蓝本筛选或关键词搜索，预览 PDF/图片，下载源文件。
3. **内容管理员制定标准**：把"编号怎么编、哪些字段必填"固化成标准，评审通过后启用；系统自动扫描存量资产，查出不合规项。
4. **部门资料征集**：管理员按部门/员工分发征集任务，员工提交文件与来源信息，文件进入待整理资产池。
5. **月度治理复盘**：管理者查看运营指标与逾期清单，导出复盘材料，形成整改行动并在下一周期验证。
6. **查找资产配套文档**：从资产详情直接查看关联的规范/作业指导书，确认当前有效版本后预览或下载。

## 2. 术语表（全局）

| 术语 | 定义 |
| --- | --- |
| 数模资产包 | 描述同一设备、组件或生产对象的记录，含业务信息和一个或多个资产文件 |
| 资产文件 | 归属于一个数模资产包的三维源模型、二维图纸、预览文件、说明文件或其他附件 |
| 适用范围 | 资产应用的产品与生产位置组合：平台（平台族+平台子类）+ 蓝本 + 基地 + 拉线 + 可选工序段 |
| 平台族 | 平台的上层业务分组：乘用车、商用车、储能、模组、圆柱 |
| 平台子类 | 平台族下用于检索和统计的标准平台值（八个标准值） |
| 蓝本 | 平台子类下可复用的标准产品及产线设计方案（如 H03、P02），同一蓝本可应用多个基地拉线；不使用"产品线"称谓 |
| 文件归组 | 确认多个上传文件属于同一份资产还是多份资产的操作 |
| 文件角色 | 三维源模型/二维图纸/预览文件/说明文件/其他附件 |
| 数据标准 | 对字段、编号、命名、值域、文件角色、验收门槛的统一规定，携带机器可读规则集 |
| 规则集 | 标准携带的规则集合，每条规则含类型、表达式、错误提示、严重级别与扫描开关 |
| BLOCKER/WARNING | 规则严重级别：阻断级（BLOCKER）提交/发布拦截，警告级（WARNING）仅进问题池 |
| 历史资料 | 从旧系统保留、可能缺少标准分类和适用范围的资产，原值持续可追溯 |
| 草稿/待整理/已标准化/已停用 | 资产生命周期四状态：草稿仅本人可见；待整理已提交可搜索；已标准化完成治理；已停用默认隐藏保留历史 |
| 数据治理 | 通过标准、责任、任务、征集、标注、确认、验收、应用，将分散文件持续转化为公司资产的管理闭环 |
| 治理任务 | 处理问题资产（清洗）或收集文件（征集）的工作单元，明确执行人、验收责任人、排期、计划数与完成数 |
| 征集记录 | 员工提交文件时的来源事实：员工、部门、任务、原始文件、来源信息、提交时间 |
| 业务确认 | 资产责任人确认资产性质、功能、文件归组、适用范围是否正确的环节 |
| 质量验收 | 按完整率、文件可用率、映射确认率、抽样准确率等指标判断治理结果是否达标的环节 |
| 正式应用 | 验收通过后以幂等作业将治理结果写入资产扩展值的过程 |
| 快照隔离 | 任务启动、扫描运行、验收轮次创建时冻结标准/字典/质量策略版本，后续变更不影响已冻结事实 |
| 遵从度 | 资产对标启用标准的达标程度，以覆盖率、规则命中率、开放问题量度量 |
| AI 就绪资产 | 完成标准化、权限确认和质量验收，可加工为 RAG 语料或其他 AI 数据产品的资产 |
| 知识文档 | 可独立检索和使用的规范、说明书、作业指导书、调试资料、验收资料或标准模板 |
| 文档版本 | 知识文档一次正式发布形成的不可覆盖内容记录；同一时间只有一个当前有效版本 |
| 资产文档关联 | 知识文档与数模资产包之间的结构化引用关系，不复制文件、不改生命周期 |
| 资产关系 | 不同数模资产之间的包含/引用/配套/替代关系 |
| 运营指标 | 由治理事实聚合的度量值，含分子、分母、可用性、统计来源与生成时间 |

## 4. 核心业务流与状态机总览（开发速览）

> 本章把全系统最关键的**业务流与状态机**集中画清楚，是开发的"路线图"。每个流程给出：触发条件 → 前置条件 → 步骤（谁做什么）→ 状态变化 → 用户反馈 → 异常分支。细节字段与规则见对应章节。

### 4.1 全系统状态机一览

| 对象 | 状态机 | 详细 |
| --- | --- | --- |
| 数模资产 | `草稿 → 待整理 → 已标准化 → 已停用`；已标准化可`重新打开`回待整理；草稿可直接删除 | 5.1 |
| 数据标准 | `草稿 → 评审中 → 已启用 → 已停用`；已启用 可修订出新版本 草稿；同编码同时只有一个 已启用 | 6.4 |
| 治理任务 | `草稿 → 进行中 → 待业务确认 → 待质量验收 → 已完成`；确认/验收退回进入返工轮次 | 9.3 |
| 治理项 | `开放 → 进行中 → 已提交 → 已确认 → 已应用`；退回回 已提交 | 9.3 |
| 确认/验收轮次 | `进行中 → 已完成`；轮次随任务轮次递增，抽样在验收轮次创建时固定 | 9.4 |
| 正式应用作业 | `待执行 → 执行中 → 成功 / 失败 / 部分成功`；失败/部分成功 可重试 | 9.6 |
| 征集任务 | `草稿 → 进行中 → 待质量验收 → 已完成` | 8.3 |
| 征集记录 | `已提交 → 已退回 / 已接收`；已退回 可补充后重提回 已提交 | 8.3 |
| 知识文档 | `草稿 → 已发布`；发布后当前有效版本唯一，新版本发布替换；文档可停用（历史保留） | 5.10 |
| AI 交付作业 | `排队中 → 执行中 → 成功 / 失败`；失败 可重试；源资产变更生成撤回/重建 | 11.3 |

### 4.2 核心业务流（步骤化）

#### 流程 A：新资料入库（上传 → 标准化）

```
[触发] 工程师有在产图纸/数模要入库
[前置] 登录且有上传权限；文件通过校验（扩展名/大小/签名/恶意内容）

步骤：
1. 工程师选择文件/文件夹上传 → 系统展示文件清单，按文件名提示归组（需确认）
2. 工程师确认归组、批量填写公共信息（平台/蓝本/基地/拉线/专业类别）、修改例外
3. 工程师 [保存草稿]（可续编）或 [提交]
   ├─ 提交成功 → 资产状态 草稿 → 待整理 → 立即可在授权范围搜索（界面提示"已提交，待整理"）
   └─ 校验失败 → 停留在当前页，红字提示缺失项，不产生待整理
4. 后台：自动扫描/人工盘点发现质量问题 → 问题池
5. 内容管理员建治理任务 → 清洗 → 资产责任人业务确认 → 内容管理员质量验收
6. 验收通过 → 正式应用 → 资产状态 待整理 → 已标准化
[异常] 单文件失败：仅失败文件可重试，已完成提交保留（见 5.4 批量上传）
```

#### 流程 B：标准制定与启用（规则 → 生效 → 对标）

```
[触发] 业务诉求：需要新规则（如编号格式、必填字段）
[前置] 编制人 = 内容管理员或授权专业代表

步骤：
1. 编制标准草稿（基本信息 + 规则集）→ 状态 草稿
2. 保存草稿时系统做影响预评估（预估受影响资产数，标注"预估"）
3. [提交评审] → 状态 评审中，结构冻结（不可编辑规则）
4. 评审人逐条通过/驳回（驳回必填意见）→ 批准人裁决
5. [启用] → 弹窗展示受影响资产清单 → 确认后：状态 已启用，固化生效时间与影响清单，同编码旧版本自动 已停用
6. 自动扫描按启用标准执行 → 违规进问题池 → 遵从度进入运营指标
[异常] 同编码同版本重复 → 409；并发版本过期 → 409；规则表达式非法 → 禁止保存
```

#### 流程 C：治理任务执行（问题 → 闭环）

```
[触发] 问题池有开放问题（扫描/盘点产生）需要处理
[前置] 内容管理员有编排权限

步骤：
1. 按问题建单创建任务（草稿）→ 维护计划项（责任人/起止/计划数）
2. 计划完整后 [启动] → 状态 进行中，计划结构锁定
3. 执行人处理治理项（原值/新值对照、单条例外）→ 治理项 已提交
4. 资产责任人业务确认（逐项，退回必填意见）→ 状态 待业务确认
   └─ 退回 → 受影响项回 已提交，进入下一确认轮次
5. 内容管理员质量验收（固定抽样 + 指标门槛）→ 状态 待质量验收
   └─ 不达标 → 受影响项进入下一返工轮次
6. 验收通过 → 正式应用作业（幂等）→ 治理项 已应用 → 状态 已完成
   └─ 部分失败 → 保留已成功项，失败项可重试
[异常] 已启动任务增删计划项/调整责任人 → 拒绝；并发更新 → 409
```

#### 流程 D：资料征集（散落文件 → 入库）

```
[触发] 部门有散落员工手中的资料需要收集
[前置] 内容管理员有征集分发权限；员工在组织同步范围内

步骤：
1. 管理员按部门/员工创建征集任务 → 草稿 → 计划完整后启动 → 进行中
2. 员工在任务入口上传文件 + 来源信息 → 生成征集记录（员工/部门/任务/文件关联）
   → 文件进入待整理资产池
3. 验收责任人检查完整度
   ├─ 通过 → 征集记录 已接收 → 进入标准治理流程（流程 A 步骤 4~6）
   └─ 退回（必填意见）→ 征集记录 已退回 → 员工补充后重提 → 已提交
[异常] 单文件失败可重试；征集记录不可覆盖（入口事实）
```

#### 流程 E：AI 数据交付（治理成果 → RAG）

```
[触发] 资产已标准化且验收通过
[前置] 资产权限范围明确、文件可用

步骤：
1. 准入检查 → 进入交付队列（记录资产版本/文件版本/权限范围）
2. 作业执行：解析 → 切片 → 索引 → 同步（记录元数据/索引状态/同步时间）
   ├─ 单文件失败 → 不阻塞成功项，失败项显示原因可重试
   └─ 全部成功 → 作业 成功
3. 源资产停用/权限变化/新版本发布 → 生成撤回或重建索引任务
[异常] 索引状态不反向覆盖资产生命周期或治理验收结果
```

#### 流程 F：月度治理复盘（指标 → 行动 → 验证）

```
[触发] 每月复盘节点
[前置] 部门管理者有查看指标权限

步骤：
1. 打开运营看板，按标准/问题类型/责任人/基地/日期筛选
2. 查看核心指标（责任覆盖率/开放问题量/逾期任务/通过率/返工率…）
3. [导出复盘] 生成只读复盘材料
4. 复盘会议形成整改行动 → 分发到责任人 → 下周期指标验证
[异常] 指标缺事实 → 显示不可用原因，不推测、不以零替代
```

### 4.3 关键交互的状态反馈表（操作 → 结果 → 反馈）

| 用户操作 | 前置条件 | 系统结果 | 界面反馈 | 冲突/失败 |
| --- | --- | --- | --- | --- |
| 提交资产 | 必填完整、编号唯一、文件校验通过 | 状态→待整理，可被搜索 | "已提交，待整理"提示 | 缺失项红字；编号重复禁止；409 |
| 启用标准 | 评审通过、并发版本有效 | 状态→已启用，旧版本 已停用 | 影响清单确认弹窗 | 版本过期 409 |
| 启动任务 | 计划完整（责任人/起止/计划数） | 状态→进行中，结构锁定 | 启动成功 | 计划缺失提示；已启动不可改计划 |
| 确认退回 | 退回意见必填 | 治理项回 已提交，进入新轮次 | 退回意见必填校验 | 空意见拒绝 |
| 验收通过 | 指标达标、抽样完成 | 触发正式应用作业 | 提交应用 | 不达标→返工 |
| 征集退回 | 退回意见必填 | 征集记录→已退回 | 员工可见退回意见 | 空意见拒绝 |
| 停用资产 | 原因必填 | 状态→已停用，默认隐藏 | 停用成功 | 无原因拒绝 |
| 停用标准 | 原因必填 | 状态→已停用，不再被引用 | 停用成功 | 无原因拒绝 |


## 5. 资产业务（系统主干）

### 5.1 数模资产包（对象与字段）

**功能目标**：资产包是系统查找、收藏、评论、使用的核心对象，描述同一个设备/组件/生产对象，可包含多个不同角色的文件。

**字段定义**：

| 字段 | 必填 | 录入方式 | 规则 |
| --- | --- | --- | --- |
| 资料编号 | 新资料必填 | 系统识别后用户确认 | 新资料全局唯一；历史冲突原样保留进入治理 |
| 资料名称 | 是 | 系统识别后用户确认 | 用户识别资料的主要名称 |
| 资产类型 | 是 | 下拉选择 | 三维模型/二维图纸/混合资产/其他资料 |
| 功能说明 | 是 | 用户填写 | 描述资产性质、功能或适用设备 |
| 专业类别 | 是 | 多选，可批量设置 | 机械/电气/液压/气动等，受控字典 |
| 适用范围 | 是 | 多选，可批量设置 | 一份资产可多个范围（见 5.2） |
| 标签 | 否 | 受控词条选择 | 管理员维护词库，用户不能自由创建 |
| 模组标签 | 条件必填 | 模组资产选择 | 仅模组及标准设备模块资产使用 |
| 标准设备模块 | 条件必填 | 责任人确认 | 标记可复用模块 |
| 关联模块数模 | 否 | 选择已有资产 | 超链接，不复制文件 |
| 设备互联编码 | 条件必填 | 选择受控设备节点 | 用于反查拉线设备互联数据 |
| 负责人 | 是 | 默认上传者，可修改 | 负责补充资料信息 |
| 资料状态 | 系统字段 | 系统/管理员更新 | 草稿/待整理/已标准化/已停用 |
| 创建人/时间 | 系统字段 | 自动 | — |

**生命周期状态机**：

```
上传/征集 ──提交──→ 待整理 ──治理完成──→ 已标准化 ──停用──→ 已停用
    │                    ↑                        │
    └──草稿（仅本人可见）  └──重新打开治理──────────┘（历史保留）
```

**业务规则**：

| 编号 | 规则 |
| --- | --- |
| R1 | 待整理不是审批状态：提交后即可在授权范围搜索使用，后台持续治理 |
| R2 | 草稿可直接删除；待整理和已标准化只能停用，不能删除 |
| R3 | 停用必填原因；停用后保留文件、收藏、评论、点赞和操作记录 |
| R4 | 已标准化资产可被重新打开为待整理（进入治理队列） |
| R5 | 历史资料缺字段时保持待整理，不自动生成业务含义 |

### 5.2 适用范围与产品/生产体系

**功能目标**：用两套独立层级表达"资料用在哪"——产品体系（平台族→平台子类→蓝本）与生产体系（基地→拉线→工序段）分离，同一蓝本可跨基地拉线复用，避免按产线复制图纸。**层级保留但不强制全填：必填分级 + 渐进式录入，缺省值进入治理补齐，不增加上传者负担。**

**结构**：`适用范围 = 平台（平台族+平台子类）+ 蓝本 + 基地 + 拉线 + 可选工序段`

**必填分级**（核心规则）：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 平台族 | 是（硬必填） | 检索主维度，不填无法提交 |
| 平台子类 | 是（硬必填） | 八个标准原子值，随平台族联动 |
| 蓝本 | 建议必填（软必填） | 区分产品方案（H03/P02）；暂无蓝本可先留空，资产进入"待整理"由治理补齐，不阻断提交 |
| 基地 | 是（硬必填） | 生产位置核心维度 |
| 拉线 | 是（硬必填） | 必须属于所选基地 |
| 工序段 | 否（可选） | 非所有资产都需要 |

**业务规则**：

| 编号 | 规则 |
| --- | --- |
| R1 | 一份资产可有多个适用范围 |
| R2 | 搜索中平台/蓝本/基地/拉线/工序段必须在同一条适用范围命中，禁止跨范围拼接 |
| R3 | 旧平台、旧拉线、旧分类只作原始文本保留和搜索，不自动推断标准值 |
| R4 | 平台族/子类/基地/拉线为硬必填；蓝本为软必填（缺失进入待整理，由治理补齐）；工序段可选 |
| R5 | 硬必填缺失 → 提交被拦截并红字提示；软必填缺失 → 允许提交，资产标记"待整理·缺蓝本"进入治理队列 |
| R6 | 软必填由内容管理员在治理流程中补齐或确认"确无蓝本"（打标跳过） |

### 5.3 资产文件与文件角色

**功能目标**：一个资产包可包含多个文件（三维源模型、二维图纸、预览文件、说明附件），按角色区分用途；PDF/图片在线预览，DOCX/DOC 服务端转 PDF 预览，其他格式下载。

**字段定义**：

| 字段 | 录入方式 | 规则 |
| --- | --- | --- |
| 原始文件名 | 自动 | 保留上传时文件名 |
| 展示名称 | 默认文件名，可改 | 详情文件列表显示 |
| 文件格式 | 自动 | PDF/PNG/DWG/STEP/X_T 等 |
| 文件大小 | 自动 | 展示和下载提示 |
| 文件角色 | 用户确认 | 三维源模型/二维图纸/预览文件/说明文件/其他附件 |
| 是否主文件 | 用户确认 | 同一资产包只能一个 |
| 是否封面 | 用户确认 | 同一资产包只能一个封面预览文件 |
| 预览能力 | 自动判断 | 支持预览或仅下载 |
| 内容摘要 | 自动 | SHA-256，上传完整性校验与重复提示 |
| 文件状态 | 自动 | 上传中/校验中/可用/失败/文件异常 |

**业务规则**：

| 编号 | 规则 |
| --- | --- |
| R1 | 同一对象的三维源模型、二维图纸、预览文件和说明附件归入同一资产包，不建立资产间关系 |
| R2 | 扩展名、大小、已知文件签名、可执行扩展名在服务端校验；校验失败文件不能进入资产包 |
| R3 | 上传完成后校验大小与内容摘要；拒绝恶意内容并说明原因 |
| R4 | 文件预览/下载经权限校验后的临时地址提供，不暴露永久存储地址与存储凭证 |

**格式支持矩阵**（当前口径，来源见 14.3 T-03 与前端上传配置）：

| 类别 | 支持格式 | 在线预览 | 说明 |
| --- | --- | --- | --- |
| 三维源模型 | X_T、STEP、STP、IGES、IGS | **封面缩略图预览（服务端渲染 PNG）+ 下载** | 详见下方"三维预览方案" |
| 二维图纸 | DWG、DXF、PDF | DWG/DXF 仅下载；PDF 可预览 | CAD 源文件首期不强制在线解析 |
| 预览图片 | PNG、JPG/JPEG、TIFF、WEBP | 是 | 浏览器直接渲染，支持翻页/缩放/全屏 |
| 办公文档 | DOCX、DOC | 是（服务端转 PDF） | 依赖 LibreOffice；转换不可用降级"暂不支持在线预览" |
| 压缩包 | ZIP、RAR | 否（仅下载） | 允许上传，不做解压解析 |

**三维预览方案（推荐：封面缩略图 + 下载，档位记录备查）**：

| 档位 | 能力 | 方案 | 成本 | 状态 |
| --- | --- | --- | --- | --- |
| 档位 0（推荐，V2.0） | 三维资产服务端渲染为**封面缩略图（PNG）**，进入"仅看可预览"检索 | OCCT 渲染投影 → 存 PNG 封面，复用转换作业基建 | 低 | ✅ 采纳 |
| 档位 1（V2.1 评估） | 在线**旋转/缩放/剖切**查看 | 服务端 OCCT 三角化导出 GLB → 前端 Three.js 渲染 | 中高 | 🟡 记录 |
| 档位 2（长期） | X_T（Parasolid）预览 | 商业 SDK（Web CAD SDK / CAD Exchanger）或 **STEP+X_T 双文件规范**（STEP 预览、X_T 下载） | 高 | 🟡 记录 |
| 档位 3（不推荐） | 纯前端解析 STEP | STEP-loader 浏览器直接解析 | 低但性能差 | ⚪ 不采纳 |

- **X_T 特殊说明**：Parasolid 为西门子私有格式，开源解析不支持；推荐"**上传时同时提供 STEP**（预览用）+ X_T（下载用）"双文件规范，避免商业 SDK 成本。
- **大模型处理**：电池模组/PACK 的 STEP 可能数十~上百 MB，档位 1 需 LOD 简化与异步转换队列；档位 0 只渲染一次 PNG，无性能压力。

**格式校验三层**：

1. 扩展名白名单（见上表）；
2. 实际文件类型魔数校验（防改后缀绕过）；
3. 大小限制 + SHA-256 摘要 + 恶意内容扫描；可执行文件（exe/bat/sh 等）一律拒绝。

> **待确认**：当前允许格式列表硬编码在前端 accept 与后端校验中，**不在字典内**（与基地/拉线不同）。若需管理员动态增删允许格式，须改为字典驱动（见 Q-35）。

### 5.4 批量上传

**功能目标**：一次选择多个文件或文件夹，通过归组、批量填写、自动识别把录入成本降到最低；单文件失败可重试，不丢整批。

**用户故事**：

- 作为**工程师**，我希望选择一个文件夹上传后系统按文件名提示归组，批量填基地/拉线/专业类别，以便上百个文件快速入库。

**核心流程**：

```
选择文件/文件夹 → 展示全部文件 → 文件归组（合并/拆分，系统建议需确认）

### 5.10 文档中心与资产文档关联

**功能目标**：规范、作业指导书等知识文档独立沉淀、版本化发布，并与数模资产建立可追溯关联；文档中心定位为资产配套说明域，不扩展为企业内容管理。

**用户故事**：

- 作为**文档维护者**，我希望用最少字段创建文档、上传首版、发布共享，以便作业指导书随设备资产一起被找到。
- 作为**用户**，我希望从资产详情直接打开关联文档的当前有效版本，以便确认"这条产线现在按哪份文件作业"。

**生命周期状态机**：

```
文档草稿 → 发布 → 已发布（当前有效版本）→ 停用（历史保留）

```

**业务规则**：

| 编号 | 规则 |
| --- | --- |
| R1 | 同一文档同一时间只有一个当前有效版本；发布新版本后原版本自动转历史 |
| R2 | 已发布版本的文件与版本号不可覆盖；内容错误通过创建新版本修正 |
| R3 | 新建文档必须显式选择全局通用或指定适用范围；指定范围须同条范围命中 |
| R4 | 发布表示进入平台共享范围，不代表工程审批、生产批准或质量会签 |
| R5 | 关联以逻辑文档 ID 为目标；文档发布新版本后关联不迁移，使用端自动读当前有效版本 |
| R6 | 解除关联不删除文档、资产、文件、评论或历史版本 |
| R7 | 无权查看一侧对象的用户不能通过关联推断其名称/编号/内容 |
| R8 | 关联建立/修改/解除记录操作人、时间、原值、新值，并使用关系版本防并发覆盖 |

| 专业类别 | ✅ 可配置 | 同上 | 一级 |
| 标签 | ✅ 可配置 | 同上（管理员词库） | 用户只能选不能建 |
| 资产类型 | ✅ 可配置 | 同上 | 受控枚举 |
| 文件角色 | ✅ 可配置 | 同上 | 受控枚举 |
| 关系类型 | ✅ 可配置 | 同上 | 名称/方向/是否重复可配 |
| **文件允许格式** | ❌ 当前硬编码 | 前端 accept + 后端校验 | 待确认是否字典化（Q-35） |

- 配置生效机制：前端检索与上传表单实时从字典 API 读取启用项，新增基地/拉线后下拉立即可用。
- 已使用值不能物理删除，只能停用（新数据不可用）或合并（历史保留指向目标）。

## 6. 数据标准管理（P0 核心功能）

### 6.1 功能目标

数据标准把业务规矩从"人脑里的经验"变成"系统能执行的规则"。有了它，三件事自动发生：

- **入库有据**：新资料提交时，不合规（编号格式错、必填缺失、命名违规）直接被拦下。
- **存量可查**：自动扫描按标准检查全部在库资产，问题自动进问题池。
- **验收有尺**：治理任务完成时，按标准定的质量门槛验收，不达标不能标记为已标准化。

### 6.2 用户故事

- 作为**内容管理员**，我希望把"资料编号必须按 `M-2311-001-A` 这种格式"固化成标准，以便扫描能自动查出不合规编号，而不是靠人翻资料。
- 作为**标准评审人**，我希望标准在生效前逐条把关，以便发布出去的标准是各专业都认可的。
- 作为**部门管理者**，我希望看到每个标准的遵从度（多少资产达标），以便知道治理重点在哪。

### 6.3 一条标准长什么样（先举例，后定义）

以最常见的"资料编号标准"为例：

> **这条标准规定**：资料编号必须匹配格式 `[类型前缀]-[序号]-[版本]`，例如 `M-2311-001-A`。
>
> - 它属于 **编码标准**（我们叫 L3 层）
> - 它**适用于所有资产类型**
> - 它带**一条规则**：编号必须匹配正则 `^[A-Z]-\d{4}-\d{3}-[A-Z]$`；不匹配时提示"编号格式应为 M-2311-001-A"
> - 这条规则是 **BLOCKER 级**：编号不合规，资料提交直接失败
> - 它有**负责人**、有**版本号**（V1、V2…）、有**变更说明**
> - 它启用时，系统会算出**有多少存量资产受影响**，先给你看清单再生效

由此归纳：**每一条标准 = 基本信息 + 若干条规则**。规则可以检查五种事：必填、命名、值域（只允许字典里的值）、文件角色、质量门槛；每条规则要么**拦截**（阻断级 BLOCKER，不让提交/发布），要么**告警**（警告级 WARNING，只进问题池提醒）。

标准按治理对象分六个层次，保证规则不混在一起：

| 层次 | 管什么 | 例子 |
| --- | --- | --- |
| L1 术语 | 概念怎么说 | "蓝本"的语义、禁止叫"产品线" |
| L2 元素 | 字段怎么定 | 功能说明：文本，1~500 字，必填 |
| L3 编码 | 编号怎么编 | 编号格式 `M-2311-001-A` |
| L4 命名 | 文件怎么命名 | 文件名 `[对象]-[类型]-[版本]` |
| L5 值域 | 允许哪些值 | 资产类型只能选 {三维模型, 二维图纸, …} |
| L6 质量 | 验收什么门槛 | 完整率 ≥ 95%、文件可用率 ≥ 98% |

### 6.4 核心流程

一条标准从想法到生效，走七步：

```
提出业务诉求 → 编制标准（草稿）→ 预评估影响 → 专业评审 → 批准 → 启用（发布）
   → 自动扫描对标 → 遵从度报告 → （季度复盘后）修订出新版本
```

状态机：

```
草稿 ──提交评审──→ 评审中 ──评审通过/批准──→ 已启用 ──修订──→ 草稿(新版本)
  │                    │                            │
  │ 直接改              │ 驳回（必填意见）            │ 停用（必填原因）
  ↓                    ↓                            ↓
（同版本改）          （回到 草稿 改）             已停用（历史保留）
```

### 6.6 业务规则

| 编号 | 规则 | 类型 |
| --- | --- | --- |
| R1 | 标准编码+业务版本唯一，重复保存返回 409 | 正常流 |
| R2 | 规则表达式保存前校验：正则语法合法、字典引用存在且启用、数值范围合法 | 正常流 |
| R3 | L5 值域标准必须引用启用中的字典项 | 正常流 |
| R4 | 状态迁移校验并发版本，冲突返回 409 | 异常流 |
| R5 | 启用必须返回受影响资产复核清单，确认后执行；清单随启用固化不可改 | 正常流 |
| R6 | 同编码同时只能有一个启用版本，启用新版本自动停用旧版本 | 正常流 |
| R7 | 停用必须填原因；停用后不再被新任务/新扫描引用，历史记录保留 | 正常流 |
| R8 | 任务启动、扫描运行、验收轮次创建时冻结当时的标准版本；之后标准变更不影响已冻结事实 | 快照隔离 |
| R9 | 阻断级（BLOCKER）规则在提交/发布时拦截；警告级（WARNING）规则只进问题池 | 执行时机 |
| R10 | 扫描只写问题池，不直接改写资产；问题按"资产+类型+目标+标准版本"生成稳定指纹，复发自动重开 | 执行时机 |

## 7. 组织与责任

### 7.1 功能目标

治理动作必须落到具体的人。本模块解决三件事：人员事实从员工系统同步进来；责任能分配、能移交；人员变动不造成任务失主。

### 7.2 用户故事

- 作为**内容管理员**，我希望把一批历史资产的负责人批量移交给新员工，以便交接不用逐个改。
- 作为**部门管理者**，我希望员工离职时他名下的治理任务自动进入移交队列，以便治理不因人员变动中断。

### 7.3 核心流程

```
员工系统 → 组织同步（员工/部门/岗位/在职状态）→ 责任分配（资产→责任人/验收人）
   → 人员变动（离职/调岗）→ 名下任务自动进入移交队列 → 管理员批量移交 → 移交记录留痕
```

### 7.4 页面与交互

**责任移交**：

```
┌─ 责任移交 ─────────────────────────────────────┐
│ 来源员工: 王五（离职待移交）  名下未完成任务: 3  │
│ ┌──────────────────────────────────────────┐ │
│ │ 任务ID   类型      数量   验收责任人  状态  │ │
│ │ #45      清洗     150    内容管理员  进行中│ │
│ │ #51      征集     50     内容管理员  进行中│ │
│ │ #62      清洗     80     内容管理员  待验收│ │
│ └──────────────────────────────────────────┘ │
│ 移交至: [赵六 ▾]                    [确认移交] │
└──────────────────────────────────────────────┘
```

- 移交后原员工名下不再有未完成任务；移交记录（原/新责任人/时间/操作人）可在操作记录中查询。

### 7.5 业务规则

| 编号 | 规则 |
| --- | --- |
| R1 | 组织同步来源为权威事实，系统不维护可覆盖副本 |
| R2 | 同步失败不阻塞既有功能，显示原因、可重试 |
| R3 | 离职/停用员工不可登录，名下未完成任务自动进入移交队列 |
| R4 | 移交必须选择新责任人；未完成治理任务不得失去责任归属 |

### 7.6 功能需求与验收

**ORG-01 组织同步（P0）**

- 功能：从员工系统同步员工（工号/姓名/部门/岗位/在职状态）与部门层级。
- 交互：后台任务执行，失败显示原因可重试；同步记录可查询。
- 验收：
  1. 员工系统更新 → 同步后员工/部门/岗位/在职状态一致。
  2. 同步失败 → 既有治理功能不受影响，显示原因、可重试。
  3. 离职员工 → 不可登录，名下任务进入移交队列。

**ORG-02 责任分配与移交（P0）**

- 功能：批量分配/移交资产责任人与验收责任人；移交必须选择新责任人。
- 交互：移交弹窗选择新责任人，见 7.4 线框。
- 验收：
  1. 批量移交 → 责任人更新且移交记录可追溯。
  2. 离职员工名下有未完成任务 → 任务进入移交队列且责任人不为空。

**ORG-03 组织维度筛选（P1）**

- 功能：治理任务、问题池、运营指标支持按部门/员工筛选，筛选只作用于同一资产范围内的事实。
- 验收：
  1. 按部门筛选治理任务 → 仅返回该部门相关任务。
  2. 员工调岗 → 历史任务按原部门归属仍可追溯。

## 9. 治理任务与执行

### 9.1 功能目标

把问题资产从"发现问题"送到"标准化入库"：问题池建单 → 任务编排 → 字段治理 → 业务确认 → 质量验收 → 正式应用。全程可追溯、可返工、失败可重试。

### 9.2 用户故事

- 作为**内容管理员**，我希望把扫描发现的 300 个编号不合规资产建成一个治理任务，分配给两名工程师，以便批量处理而不是逐个改。
- 作为**资产责任人**，我希望对清洗结果逐项确认，以便我负责的资产业务含义没有被人改错。

### 9.3 核心流程

```
扫描/盘点发现 → 问题池（稳定指纹去重）→ 开放问题建单 → 任务编排（计划项/责任人/排期）
   → 字段治理（原值/新值对照，单条例外）→ 业务确认（逐项，退回必填意见）
   → 质量验收（固定抽样+指标门槛）→ 通过 → 正式应用（幂等作业，失败重试）
   → 未通过 → 返工轮次（只带入受影响项）
```

### 9.5 业务规则

| 编号 | 规则 |
| --- | --- |
| R1 | 任务创建为草稿；计划完整（责任人/起止/计划数，至少一项）后才能启动；启动后结构锁定 |
| R2 | 任务进度来自治理项状态聚合，单一事实来源 |

**GOVTASK-01 任务编排（P0）**

- 功能：创建任务（草稿）→ 维护计划项（责任人、起止日期、计划数）→ 计划完整后启动 → 结构锁定 → 执行进度更新。
- 验收：
  1. 计划不完整 → 启动校验失败并提示缺失项。
  2. 已启动任务新增/删除计划项或调整责任人 → 拒绝。

**GOVTASK-02 进度事实（P0）**

- 功能：任务进度来自治理项状态聚合，列表展示与详情一致。
- 验收：
  1. 治理项完成 → 任务进度随之更新且与列表一致。

**GOVTASK-03 确认与验收闭环（P0）**

- 功能：业务确认（逐项保存、退回必填意见、批量通过不丢失）→ 质量验收（固定抽样、指标分子分母、返工只带入受影响项）→ 正式应用（幂等、部分失败保留已成功项、可重试）。
- 验收：
  1. 验收抽样在轮次创建时固定，页面不可删除。
  2. 应用失败 → 保留已成功项，重试幂等。

## 11. AI 数据交付

### 11.1 功能目标

把治理好的资产交付给 RAG 平台做语料。只有已标准化、权限明确、文件可用的资产才能进队列；解析、切片、索引逐文件执行，失败不阻塞、可重试；源资产变化自动撤回或重建索引。

### 11.2 用户故事

- 作为**内容管理员**，我希望把已标准化资产推送到 RAGFlow，以便公司检索增强问答能用到图纸知识。
- 作为**系统运维**，我希望某个文件解析失败不影响整批，且能单独重试，以便交付不因单点失败中断。

### 11.3 核心流程

```
已标准化资产 → 准入检查（标准化/权限/文件可用）→ 进入交付队列
   → 解析 → 切片 → 索引 → 同步（记录版本/元数据/索引状态）
   → 源资产停用/权限变化/新版本 → 撤回或重建索引
   → 失败项幂等重试，不阻塞成功项
```

```

### 11.5 业务规则

| 编号 | 规则 |
| --- | --- |
| R1 | 仅已标准化、权限范围明确且文件可用的资产可进入交付队列 |
| R2 | 交付记录资产版本、文件版本、解析/切片/索引版本、元数据、访问范围、索引状态、最近同步时间 |
| R3 | 单文件失败不阻塞成功项；失败项显示原因、可幂等重试 |
| R4 | 源资产停用/权限变化/新版本发布 → 生成撤回或重建索引任务 |
| R5 | 索引状态不反向覆盖资产生命周期或治理验收结果 |
| R6 | 交付作业全量留痕，重试通过 retryOf 关联原作业 |

### 11.6 功能需求与验收

**AI-01 AI 就绪准入（P0）**

- 功能：仅已标准化、权限范围明确且文件可用的资产可进入交付队列，携带资产版本、文件版本、权限范围。
- 验收：
  1. 未标准化/无权限/文件不可用 → 不在交付队列。
  2. 已就绪资产 → 可入队且信息完整。

**AI-02 RAGFlow 交付作业（P0）**

- 功能：记录解析、切片、索引、同步版本、元数据、访问范围、索引状态、最近同步时间；失败项不阻塞成功项，可幂等重试；源资产停用、权限变化、新版本发布时生成撤回/重建任务。
- 验收：
  1. 单文件解析失败 → 其余文件继续，失败项显示原因、可重试。
  2. 源资产停用 → 生成撤回任务。
  3. 索引状态不反向覆盖资产生命周期或治理验收结果。

**AI-03 交付审计（P1）**

- 功能：交付作业全量留痕（作业类型、资产/文件版本、触发原因、结果、重试来源）。
- 验收：
  1. 作业执行 → 审计记录含触发原因与结果。
  2. 重试 → 新作业通过 retryOf 关联原作业。

### 12.2 数据范围判定规则

- 用户数据范围按**蓝本或基地**配置（ADR-0004）。
- 用户可访问一份资料，当且仅当该资料**至少一个适用范围**命中用户授权的蓝本或基地。
- 搜索、预览、下载、直链访问分别执行数据范围校验，不依赖前端隐藏。
- 征集分发范围受内容管理员数据范围约束；员工只能看到分发给自己的征集任务。
- 关系图/关系列表只展示用户有权查看的关联资产；无权资产不泄露名称/编号/适用范围/文件信息。

## 15. 技术设计范围声明（数据模型/API 移出 PRD）

> 本章是 PRD 的技术边界声明。**数据模型、API 契约、组件设计、搜索方案等技术方案不属于 PRD，移入技术设计文档（`docs/technical-design.md` V2.0 章节），并在第 16 章开放问题确认后重新设计，不沿用 V1.8 已实现的代码结构作为权威。**

### 15.1 为什么移出 PRD

1. **职责分离**：PRD 只回答"做什么、为什么、给谁用、什么规则"；"用什么表、什么字段、什么接口"是技术设计（TDD）的职责。业务方评审应聚焦业务决策，不被技术细节干扰。
2. **避免过早锁定**：技术方案在业务规则确认后设计，避免用旧实现框住新需求。V1.8 迁移 SQL 是历史实现，不代表 V2.0 的最优方案。
3. **保持演进空间**：V2.0 新增能力（组织同步、征集、AI 交付、规则引擎化标准）可能需要全新技术方案（员工数据源、调度器、规则执行引擎、存储策略），PRD 不预设实现。

## 17. 业务闭环落地与验证

> 产品做出来 ≠ 业务闭环落地。本章定义系统上线后如何验证闭环真正转起来、如何衡量成功、如何让用户用起来。**本章由业务负责人与管理者确认（Q-32~Q-34）。**

### 17.1 端到端业务闭环场景（验证"闭环成立"）

系统不是由独立功能拼成的，必须有一条可走通的全链路。以下场景用于验收"治理闭环真正闭合"：

| 编号 | 端到端场景 | 验证要点 |
| --- | --- | --- |
| E2E-01 | 新资料从上传到标准化 | 上传 → 归组 → 提交（待整理）→ 标准扫描发现问题 → 治理任务 → 清洗 → 业务确认 → 质量验收 → 正式应用 → 已标准化 → 可被检索/交付 AI |
| E2E-02 | 标准变更驱动存量治理 | 新标准启用 → 影响复核清单 → 受影响资产进问题池 → 建任务 → 治理闭环 |
| E2E-03 | 征集驱动新资产入库 | 征集任务分发 → 员工提交 → 征集记录 → 待整理池 → 标准治理流程 |
| E2E-04 | 人员变动不中断治理 | 员工离职 → 移交队列 → 批量移交 → 任务继续执行 → 指标责任归属正确 |
| E2E-05 | 治理成果反哺 AI | 已标准化资产 → AI 交付队列 → 解析/切片/索引 → 源资产变更 → 撤回/重建 → 索引与生命周期一致 |
| E2E-06 | 月度复盘闭环 | 看板指标 → 导出 → 复盘 → 整改行动 → 责任人 → 下周期指标验证 |

**验收标准**：每条 E2E 场景在约定测试数据下完整走通，任一环节失败即视为闭环未闭合。

### 17.2 试点计划（先跑通，再铺开）

| 阶段 | 内容 | 评估标准 |
| --- | --- | --- |
| 试点准备 | 选 1 个基地或 1 条拉线 + 1 个部门（如设备科），准备迁移数据与测试数据 | 数据就绪、角色就位 |
| 试点运行（4 周） | 跑通 E2E-01~06；内容管理员实际制定标准、建任务；工程师实际上传/征集 | 端到端场景通过率、用户反馈 |
| 试点评估 | 对照 Q-33 成功指标评估；收集痛点 | 指标达到试点目标值 |
| 铺开决策 | 试点通过则分批次铺开（按基地/部门）；未通过则复盘修正后重试 | 管理层决策记录 |

### 17.3 成功指标（北极星）

> 北极星指标建议由业务负责人从以下候选中选定 1 个主指标 + 3~5 个辅助指标。

| 候选指标 | 定义 | 用途 |
| --- | --- | --- |
| 资产标准化率 | 已标准化资产 / 全部在库资产 | 治理闭环整体进度（主指标候选） |
| 问题平均关闭周期 | 问题关闭耗时均值 | 治理效率 |
| 一次验收通过率 | 首轮通过任务 / 验收任务 | 治理质量 |
| 标准遵从度 | 达标资产 / 范围内资产 | 标准落地程度 |
| AI 语料可用率 | 可交付资产 / 已标准化资产 | 治理价值反哺 |
| 资料复用率 | 被检索/下载/关联的资产占比 | 资产使用价值 |

### 17.4 运营推广与组织保障

| 机制 | 说明 |
| --- | --- |
| 上传激励 | 工程师提交资料计入部门贡献；试点阶段设专项激励（确认 Q-34） |
