## Problem Statement

资产平台里的资料（资产文件附件、知识文档）要靠人逐条阅读才能整理归类、才能被找到。普通用户在「描述一个东西但说不清它的规范名称」时找不到对应资产，提交人上传后要手工填写一堆元数据才能让资产进入待整理，内容管理员要逐份资料人工判断分类与命名是否规范，部门里"某设备异常该怎么处理、某工艺参数窗口是多少"这类问题散落在文档里没有人能快速回答。ep 需要有 AI 能力：能对着资料问答、能自动给出编目建议，但**绝不能直接写业务库**——一切写入先成建议、由人确认后再生效，并且用户只能看到自己范围内（AssetScope）的内容。

## Solution

ep 内新增「AI 智能体」功能区（一期）：

1. **智能问答**：用户在工作台用自然语言提问，ep 后端把问题连同用户 AssetScope 检索边界转发给独立部署的 AI 能力服务，以 SSE 流式返回带来源引用的回答；会话与消息落 ep 库（真源）。范围外资料既不检索也不回答，能力服务不可用时明确降级提示且不丢会话。
2. **AI 编目建议**：资产文件/知识文档成功入库后，异步触发解析与元数据抽取；抽取结果以「AI 建议」形态落入 ep 的待确认区（不直接改业务数据），建议可确认/驳回/重新生成；确认后由 ep 现有资产写入链路生效并留操作日志。
3. **建议-确认工作台**：统一清单页按状态筛选、跳转到目标资产；上传与资产详情处提供轻量入口。
4. 越权与审计：建议目标必须落在当前用户 AssetScope 内，范围外不可见、不可确认；AI 全部动作可审计。

前端只调用 ep 后端（浏览器永不直连 AI 能力服务）；AI 能力服务在本期以「既定契约 + fake/stub」对待（见 §Implementation Decisions）。

## User Stories

问答：

1. 作为平台用户，我想在工作台用自然语言提问，以便不用记住资产的规范名称就能找到答案。
2. 作为平台用户，我想看到回答是流式逐字出现的，以便长回答不用等全部生成完才读。
3. 作为平台用户，我想回答里带来源引用（哪份文档、哪个片段），以便判断答案可信并可点开原文核对。
4. 作为平台用户，我想在提问后继续追问上一轮的话题，以便同一个问题域内连续深挖（会话内上下文）。
5. 作为平台用户，我想我的会话历史下次回来还在，以便中断后能接着上次继续问。
6. 作为平台用户，我想在会话里删除或重命名我的会话，以便管理自己的工作痕迹。
7. 作为平台用户，我想问答结果只覆盖我有权限的资料，以便不会看到或推导出范围外内容。
8. 作为平台用户，当问题超出语料或证据不足时，我想得到明确的"无法回答"而不是编造的答案，以便不误导现场决策。
9. 作为平台用户，当 AI 能力服务不可用或超时时，我想看到明确的降级提示并能重试，以便知道是系统问题而非我提问有误。
10. 作为平台用户，我想引用卡片能跳转到对应文档/资产的预览页，以便核实原文上下文。
11. 作为平台用户，我想看到我发出问题的历史消息和 AI 回答都能滚动回看，以便对话上下文完整。
12. 作为资产资料责任人，我想在我范围内提问得到的回答可追溯到具体文件版本，以便确认引用的不是过期版本。

编目建议：

13. 作为上传者，我上传资产文件成功后系统自动触发 AI 整理，以便不用我手工逐条填元数据。
14. 作为上传者，我想上传后能收到"AI 正在整理、完成后会出现在建议清单"的提示，以便知道后续去哪里看结果。
15. 作为内容管理员，我想看到 AI 对资产给出的命名/分类/标签/摘要/范围等建议及依据片段，以便快速判断是否采纳。
16. 作为内容管理员，我想逐条确认 AI 建议使其生效到资产，以便保证入库元数据经过人审。
17. 作为内容管理员，我想逐条驳回不满意的 AI 建议，以便不被错误建议污染资产数据。
18. 作为内容管理员，我想对一条资产重新请求 AI 整理，以便在修改资料或换语料后重试。
19. 作为内容管理员，我想看到 AI 建议的来源与置信度，以便对低置信建议加倍人工核对。
20. 作为知识文档作者，我想新建/新版本知识文档发布后也能触发 AI 编目建议，以便文档中心同样受益。
21. 作为资产责任人，我确认建议后资产的变更进入现有生命周期与操作日志，以便治理留痕与"提交可用、后台治理"不被破坏。
22. 作为上传者，我想 AI 建议只作用于我自己范围内的资产，以便不产生跨范围的数据变更风险。

建议-确认工作台与入口：

23. 作为内容管理员，我想在建议清单页按状态（待确认/已确认/已驳回）筛选，以便优先处理堆积的待确认项。
24. 作为内容管理员，我想清单里的每一项都能跳到目标资产详情，以便对照资产现状做判断。
25. 作为内容管理员，我想在资产详情页直接看到该资产的 AI 建议并可确认/驳回，以便不必跳去清单页处理。
26. 作为平台用户，我想在首页/导航能进入「AI 智能体」工作台，以便能力入口稳定可达。
27. 作为治理人员，我想 AI 相关的全部动作（谁触发了什么、确认了什么、结果如何）可审计，以便合规追溯。

权限与安全：

28. 作为普通用户，我想在问答与建议清单中都看不到任何范围外资料的建议与片段，以便不越权。
29. 作为普通用户，即使我构造提问试探，系统也不该用我范围外的语料作答（拒答/过滤），以便守住数据边界。
30. 作为管理员，我想 AI 能力服务的连接密钥/地址只在后端配置，以便浏览器与前端代码永远不接触它。
31. 作为管理员，我想在能力服务不可用时平台其余功能不受影响，以便 AI 故障不拖垮主链路。
32. 作为系统管理员，我想 AI 会话与建议数据随用户权限回收逻辑一致（离职/范围变更即不可见），以便数据生命周期可控。

## Implementation Decisions

以下为已拍板的实现决策；不含文件路径（可能过时）。架构出处见架构笔记 D1~D6、d1~d6。

### 模块（ep 仓库内新增「ai」域，沿用现有 `api/application/infrastructure/domain` 分层与命名习惯）

- **后端 ai 域**
  - api：问答 SSE 端点、会话端点、建议清单/确认/驳回端点、内嵌查询端点（单目标建议）。
  - application：会话服务、建议服务、异步触发编排。
  - domain：AI 建议实体（状态机见下）、会话/消息实体、仓储接口；**建议只落在当前用户 AssetScope 内**的规则放在这里。
  - infrastructure：内存仓储（默认 dev profile）+ JDBC 仓储（local/oceanbase，沿袭现有仓储先例）；**能力服务客户端实现**；入库触发的 Job 通过现有治理 JobDispatcher 机制投递，不新建队列。
- **外部 AI 能力服务 = Port**：`AiCapabilityClient` 接口（检索问答流式 / 文档入库 / 抽取编目），实现走 HTTP+SSE 到泛化后的能力服务；测试一律注入 fake。真实联调依赖泛化工作流交付的契约（另见 Out of Scope）。
- **前端 ai 功能区**：`/ai` 问答工作台（会话侧栏 + 流式对话 + 引用卡）、`/ai/suggestions` 建议-确认清单、上传成功提示与资产详情建议区的轻量内嵌入口。api 客户端只调 ep 后端。

### HTTP 契约（主缝，前端照此对接）

```
POST /api/ai/chat                              → SSE 流（含建会话/续会话）
GET  /api/ai/sessions                          → 会话列表
DELETE /api/ai/sessions/{id}                   → 删除会话
PATCH /api/ai/sessions/{id}                    → 重命名会话
GET  /api/ai/sessions/{id}/messages            → 历史消息（含引用）
GET  /api/ai/suggestions?status=&targetType=&targetId= → 建议清单（分页+筛选）
POST /api/ai/suggestions/{id}/confirm          → 确认（触发资产动作）
POST /api/ai/suggestions/{id}/reject           → 驳回
POST /api/ai/targets/{type}/{id}/suggestions/regenerate → 对单目标重新整理
```

SSE 事件契约（三层同构，浏览器按此消费）：

```
event: meta      { sessionId, messageId }
event: delta     { text }            （可多次）
event: citations { refs: [{docId, 位置, 摘录, 权限内}] }
event: done      { usage }
event: error     { code, message }   （降级/超时/鉴权失败）
```

### AI 建议实体与状态机（来自决策，原样保留）

```
AI 建议状态机:  PENDING(待确认) ──confirm──▶ CONFIRMED(已确认) ──▶ 资产动作已应用
                     │
                     └──reject──▶ REJECTED(已驳回)
  （同目标重复整理：新建议重新进入 PENDING，旧待确认建议作废为 SUPERSEDED）
```

建议载荷（能力服务 `/extract` 返回，ep 落库并展示）：

```
AiSuggestion {
  targetType: ASSET | KNOWLEDGE_DOC
  targetId, targetScope,          // 目标自身的 AssetScope，入库时写入
  proposed: { title?, assetType?, tags[], summary?, scopeHints? },  // 仅资产支持字段
  evidence: [片段], confidence,    // 依据与置信度
  source: "AI",                    // 与人工来源区分
  status: PENDING
}
```

### 权限、范围与审计

- scope 注入点：ep 的 ai 应用服务组装（controller 只取当前登录用户）；发给能力服务的检索请求**携带用户 AssetScope 过滤条件而非用户身份**。
- 越权规则（应用层强制）：建议目标（资产/文档）必须落在当前用户 AssetScope 内，范围外建议在清单与详情均不可见、不可确认/驳回；问答检索由能力服务按注入的 scope 过滤，能力服务不感知用户。
- 确认动作：调用现有资产写入/文档发布链路的方法完成生效，**不得新开旁路写库**；随后写操作日志（现有审计机制），记录 AI 来源与依据快照。
- 会话真源：消息与引用落 ep 库；本期不做 Redis 热层（d3），但存储经仓储接口，未来可替换。
- 能力服务密钥与 base URL 仅存在于后端配置（沿用 `.env.example` 式管理，不提交真实值）。

### 异步与降级

- 入库触发：资产文件上传成功 / 知识文档发布成功后，经现有 JobDispatcher 投递「解析入库+抽取编目」Job；失败可重试，建议落库后即与 Job 解耦。
- 问答降级：能力服务超时/不可用 → SSE `error` 事件 + 界面明确提示可重试；ep 主链路与现有功能不受影响。

## Testing Decisions

- 好测试的定义：**只测外部行为，不测实现细节**。后端 = HTTP 契约（状态码、SSE 事件序、越权 403、降级 error）；前端 = 用户可见行为。
- **主缝 = API 层**（HTTP 黑盒，fake `AiCapabilityClient` + 内存仓储；先例：`AssetControllerTest`、`DocumentControllerTest` 的 MockMvc 风格）。每条验收型用户故事至少一条 API 层测试收口：SSE 事件序（meta→delta→citations→done/error）、未登录 401、范围外建议 403/不可见、确认后资产动作与操作日志。
- 底层单测照常保留（金字塔底座，非主缝）：建议状态机与越权规则在 application/domain 层直接测（先例：`GovernanceConfirmationServiceTest` + `GovernanceTestFixture`）；仓储实现分别测内存与 JDBC（先例：`InMemoryDocumentRepositoryTest`/`JdbcDocumentRepositoryTest`）。
- Job 触发：复用治理 JobDispatcher 的既有测试先例（`GovernanceApplicationJobServiceTest` 风格）。
- 前端：ai 功能区组件级测试覆盖关键交互（发送/流式渲染/引用跳转/建议确认按钮态），其余 UI 行为按仓库规则走浏览器证据验收。
- 明确不做：不把真实 AI 能力服务放进单元/集成测试；两仓联合验收留到泛化工作流交付后的独立阶段。

## Out of Scope

- ai-rag 能力服务泛化（namespace 化、编目/抽取端点、评测集、契约落地）= **独立前置工作流**（另开计划文件排期；本 spec 以既定契约 + fake/stub 联调对待）。
- 二期全部内容：编排层（L2）、治理/盘点助手、Redis 热层、OTel 观测、MCP 工具注册表、agent 评测门禁。
- 数模/图档二进制全文问答（只做元数据编目）；跨语料联合检索（电池语料不接入）。
- 知识资产沉淀（知识卡/FAQ/术语）、多产品多租户、移动端适配。
- 会话热缓存与 token 成本优化（d3 后置项）。

## Further Notes

- 本 spec 与架构笔记同源：范围=架构笔记「一期」，自治边界= D1（建议-确认分层），会话= D6（库为真源）。
- 一期验收的端到端前提是泛化后的能力服务（或其 stub）可按契约联通；ep 侧先以 fake 全量自测，避免阻塞。
- 语义提醒：本文中「资产」= 数模资产平台主体（含资产文件附件）；「知识文档」= 文档中心文档；「范围」= AssetScope（平台/产品线/蓝本/基地/拉线/工序段）。语料 = 可解析文本类（Office/PDF/文本），入库时随目标携带其自身 scope。
