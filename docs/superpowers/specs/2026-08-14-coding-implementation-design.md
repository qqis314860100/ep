# Coding Implementation 融合方法论与 Skill 设计

## 1. 目标

创建通用 Agent Skill `coding-implementation`，把风险自适应 R2C 变更流水线与
AI Project Harness 融合为一套可执行、可验证、可复用的 Vibe Coding 工程方法论。

交付顺序必须固定：

1. 定义融合方法论、风险路由和 Gate 契约。
2. 创建并打包通用 Skill。
3. 使用公开评分规则反复校验 Skill，达到 100/100。
4. 使用通过校验的 Skill 审计并重新整理 `ep` 项目。
5. 验证 `ep` 落地结果并提交变更。

Skill 通过验证之前，不得以其名义修改 `ep` 的流水线资产。

## 2. 核心模型

采用两个正交维度：

- R2C 是纵向生命周期，回答一次变更如何从意图到可验证交付。
- Harness 是横向运行环境，提供仓库记忆、知识、工具、护栏、反馈和治理。

生命周期统一为：

```text
intake -> clarify -> specify -> plan -> apply -> verify -> archive
```

阶段名称保持稳定，但按风险合并执行：

| 路径 | 适用范围 | 阶段要求 |
| --- | --- | --- |
| Fast | 低风险、局部、可逆且需求明确 | 合并 intake/clarify/specify/plan，保留 apply/verify/archive |
| Standard | 普通功能、接口或跨文件修改 | 完整阶段，可合并相邻文档产物 |
| Strict | 数据、权限、安全、公开契约、跨模块或不可逆变更 | 完整阶段，增加人工设计 Gate、回滚方案和行为证据 |

风险不得只根据“新增”或“修改”判断。路由至少考虑需求歧义、影响范围、数据变更、
权限与安全、公开契约、生产影响和可逆性，并允许用户显式覆盖。

## 3. Gate 契约

每个阶段必须定义输入、动作、最小产物、自动检查、人工确认条件和退出证据。
Gate 约束结果，不固定 Agent 的实现步骤。

| 阶段 | 最小退出证据 |
| --- | --- |
| intake | 目标、范围、风险路径和选择理由 |
| clarify | 已解决歧义、显式假设和剩余问题 |
| specify | 可观察验收场景、约束和非目标 |
| plan | 影响面、实现切片、验证方式；Strict 另含回滚方案 |
| apply | 小批次变更及相应的定向检查结果 |
| verify | 静态检查、测试、行为证据、剩余风险和人工 Gate 状态 |
| archive | 提交或评审摘要；必要时更新 ADR、规则或 Skill |

若产品行为无法机械验证，必须保留截图、日志、前后对比或人工确认。测试通过不能代替
产品行为确认。

## 4. Skill 结构

安装目录为 `/Users/tomtong/.codex/skills/coding-implementation/`：

```text
coding-implementation/
├── SKILL.md
├── references/
│   ├── methodology.md
│   ├── risk-routing.md
│   ├── gate-contract.md
│   └── scoring-rubric.md
├── scripts/
│   ├── score_skill.py
│   └── audit_project.py
└── assets/
    └── project-template/
        ├── .ai/
        │   ├── pipeline.yaml
        │   └── templates/
        └── .prompt/
            ├── 工作流/
            ├── 技术方案/
            ├── 数据层/
            ├── 业务层/
            ├── 应用层/
            ├── 审查/
            └── 工程结构.md
```

`SKILL.md` 只保存执行流程和资源导航。详细方法论、风险算法、Gate 定义和评分规则按需
读取，避免每次触发都占用大量上下文。

`.prompt/` 保存阶段产物的生成与审查模板，不作为项目事实来源。项目事实仍以
`AGENTS.md`、需求文档、技术设计、ADR、代码和测试为准。

## 5. 可执行工具

### 5.1 Skill 评分

`score_skill.py` 对以下维度确定性评分：

| 维度 | 分值 |
| --- | ---: |
| Skill 结构与触发描述 | 15 |
| 方法论一致性与术语 | 15 |
| 风险自适应路由 | 15 |
| Gate 与证据契约 | 20 |
| Harness、反馈和人类 Gate | 15 |
| 渐进披露与模板完整性 | 10 |
| 可执行验证与可移植性 | 10 |

只有总分 100、Skill 规范验证通过、所有脚本测试通过、场景测试通过且打包成功，才允许
进入 `ep` 应用阶段。评分脚本必须同时输出扣分原因和修复建议，不能只有总分。

### 5.2 项目审计

`audit_project.py` 检查项目是否具备：

- 简短且可导航的 Agent 入口。
- 需求、架构、ADR 和领域术语来源。
- 风险路由配置、变更状态和最小产物模板。
- lint、typecheck、test、build 等确定性 Sensor。
- 数据、权限和危险命令护栏。
- 产品行为的人类确认和证据位置。
- 决策、漂移和经验沉淀机制。

审计器只读运行，不连接数据库、不执行产品构建，也不修改目标仓库。

## 6. 场景验证

至少使用以下场景验证路由和产物：

1. 修改一处明确文案，应进入 Fast。
2. 新增普通检索条件，应进入 Standard。
3. 修改数据库结构或旧数据兼容逻辑，应进入 Strict。
4. 修改权限或下载安全策略，应进入 Strict 并要求人工 Gate。
5. 用户显式提高流程等级时必须接受；降低等级时必须记录被覆盖的风险。

测试必须覆盖正常评分、缺失资源、错误目录、无效配置和未满足 Gate 等失败路径。

## 7. ep 应用范围

Skill 达标后，对 `ep` 执行以下整理：

1. 审计当前 Guides、Sensors、Guardrails、行为 Gate 和治理记录。
2. 保留现有 `AGENTS.md`、`CONTEXT.md`、`requirement.md`、技术设计和 ADR 的事实地位。
3. 新增项目级 `.ai/pipeline.yaml`、变更模板和 `.prompt/` 分层模板。
4. 更新 `AGENTS.md`，增加风险路由、按任务读取和流水线入口，但不复制完整方法论。
5. 增加本地可执行的项目流水线检查，使仓库不依赖个人 Skill 安装也能验证结构。
6. 运行项目审计和最小相关检查，修复至项目规则下 100/100。

本次不修改前后端业务行为、数据库 schema 或生产配置，不引入平台专用的 Agent 编排。

## 8. 错误处理与安全边界

- 缺少项目事实时停止相关阶段，不编造需求或架构。
- 自动检查失败时保留失败证据并修复根因，不通过降级检查获得通过状态。
- Strict 变更缺少人工确认时保持待确认，不将流程标记为完成。
- 不把凭据、环境文件、上传数据、构建产物或浏览器生成物写入归档。
- Skill 评分 100/100 只代表满足公开规则，不代表所有未来业务变更绝对正确。

## 9. 提交边界

设计规格、通用 Skill 和 `ep` 应用是三个独立可验证版本：

- 设计规格单独提交。
- 通用 Skill 安装在个人 Skill 目录并生成可分发 `.skill` 包；不混入 `ep` 提交。
- `ep` 的文档、模板和检查脚本作为 Harness 变更单独提交。
