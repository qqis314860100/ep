# 数据治理下一阶段设计

## 1. 背景与结论

当前平台已经具备问题建单、任务编排、字段处理、业务确认、质量验收、返工轮次、异步正式应用和审计存储的闭环骨架，但还不能作为完整、常态化的数据治理平台。

下一阶段采用两期推进：

1. 第一期修复现有闭环的可信度，让流程可理解、进度真实、依赖方向正确、历史任务不伪装为闭环任务。
2. 第二期补齐标准中心、映射规则、自动扫描和治理运营，使问题发现、处理和复盘能够常态化。

第一期通过验收后才能启动第二期。第二期的四个能力分别编写规格和实施计划，不作为一个大版本一次交付。

本设计是对 `2026-07-27-governance-task-gantt-design.md` 的纠偏和后续演进。两者冲突时以本设计为准，具体包括：执行中及后续状态不再默认表格；计划进度不再直接信任原始计划接口；第一期允许调整后端计划投影契约。旧设计中关于只读甘特、计划锁定、日期基线和响应式布局的约束继续有效。

## 2. 领域边界

数据治理是围绕数据标准、责任、问题、处理结果和质量门槛形成的持续管理机制，不等同于数据清洗、审批或项目管理。

平台负责：

- 固化标准、字典、责任和治理范围。
- 发现并追踪数据质量问题。
- 保存原始事实和拟变更结果。
- 组织业务确认、质量验收、返工和正式应用。
- 记录规则版本、操作人、时间、原值、新值和阶段决定。

平台不负责：

- 自动推断未知业务含义。
- 替代业务责任人作歧义判断。
- 将治理确认解释为工程审批或生产批准。
- 允许自动规则绕过验收直接覆盖正式数据。

## 3. 已确认问题清单

### 3.1 P0：甘特依赖箭头方向错误

依赖路径从前置计划右边缘出发，先向右绕行，再从右向左进入后续计划，SVG 的 `markerEnd` 因而自动朝左。

任务 1 的实际路径为：

```text
dependency-101-102: M108,28 H118 V84 H108
dependency-102-103: M360,84 H370 V140 H360
```

两条路径的最后一段都向左。当前测试只断言依赖路径存在，没有验证路径终段方向。

### 3.2 P0：甘特进度存在两个事实来源

`GET /api/v1/governance/tasks/{taskId}` 会按治理项聚合计划状态和完成量；`GET /api/v1/governance/tasks/{taskId}/plans` 直接返回计划存储值。前端甘特图使用后者。

任务 4 已完成时已经出现矛盾：

| 来源 | 计划状态 | 完成量 |
| --- | --- | --- |
| 任务详情投影 | `DONE` | `2/2` |
| 独立计划接口 | `NOT_STARTED` | `0/2` |

甘特图可能把已完成计划显示为未开始，违反“进度来自治理项状态聚合”的产品规则。

### 3.3 P0：历史任务被展示为完整闭环任务

任务 1 的工作流版本是 `LEGACY_PROGRESS`，只保留历史汇总进度，不支持逐项业务确认和质量验收。当前里程碑组件只接收任务状态，不接收工作流版本，因此仍展示“计划锁定、业务确认、质量验收、正式应用”。

这会向用户暗示历史任务具有并不存在的闭环证据。

### 3.4 P1：流程只展示标签，没有表达责任交接

当前四个里程碑是互不相连的标签，没有展示：

- 当前阶段、阶段负责人和阶段完成条件。
- 数据处理提交后为什么进入业务确认。
- 业务确认通过后为什么进入质量验收。
- 确认或验收退回后如何进入新返工轮次。
- 正式应用失败为什么可以逐项重试。

用户能看到状态名，但无法理解治理结果如何成为正式标准值。

### 3.5 P1：核心计划工作区被弱化

- 页面默认固定为表格，即使任务已经执行。
- 甘特切换位于页面较低位置，入口弱。
- 空问题集合和原始 JSON 范围快照占用主要垂直空间。
- 执行中的排期、依赖和风险不能在进入页面后立即看到。

### 3.6 P1：标准化能力不完整

平台已有基础字典、规则快照和质量策略领域对象，但还没有完整的数据标准管理工作台。标准的版本、生效范围、负责人、影响数量和变更说明不能形成统一运营入口。

### 3.7 P1：映射规则没有形成产品闭环

需求已经定义旧值到标准值的映射规则，但当前没有完整的映射维护、确认、停用、适用范围和影响分析工作台。系统不能将已确认映射稳定复用于后续治理。

### 3.8 P1：问题发现尚未常态自动化

当前问题池主要依赖种子数据或显式写入，没有周期扫描机制来持续发现缺失字段、非法值、重复资产、异常文件、失效责任人和标准变更影响。

### 3.9 P2：治理运营机制不完整

当前缺少统一运营视图来持续跟踪责任覆盖率、问题关闭周期、一次确认通过率、验收通过率、自动处理率、问题复发率和正式应用成功率，也没有在平台中体现每日、每周、每月和季度治理节奏。

## 4. 第一期：闭环可信度修复

### 4.1 目标

让现有字段治理闭环做到：用户看得懂流程、页面展示真实状态、依赖关系方向正确、不同工作流版本不会混用语义。

### 4.2 权威计划视图

后端建立唯一的 `GovernancePlanView` 投影，包含计划基线字段和治理项聚合字段：

- 计划 ID、名称、责任人、计划日期、实际日期、数量单位、依赖和问题 ID。
- 聚合状态 `NOT_STARTED | IN_PROGRESS | BLOCKED | DONE`。
- 聚合完成量和完成比例。
- 逾期及无效依赖所需的原始字段。

任务详情和独立计划接口必须复用同一投影函数，禁止一个接口返回聚合值、另一个接口返回存储值。计划存储中的状态和完成量不作为闭环任务的展示事实。

历史任务继续使用历史计划存储值，并在响应中明确 `workflowVersion=LEGACY_PROGRESS`。

### 4.3 依赖路径

依赖含义保持为“后续计划依赖前置计划”。箭头从前置计划右侧出发，进入后续计划左侧，终段必须向右。

- 计划之间有足够水平间距时使用正向折线。
- 计划相邻、重叠或日期顺序与依赖顺序不一致时使用绕行路径。
- 无论采用哪种路径，进入目标计划的最后一段必须从左向右。
- 路径计算提取为纯函数，测试直接验证起点、终点和终段方向，不只验证 SVG 元素存在。

### 4.4 闭环流程步骤

`CLOSED_LOOP_V1` 使用连接式步骤展示：

```text
任务编排 -> 数据处理 -> 业务确认 -> 质量验收 -> 正式应用 -> 完成
                         |              |
                         +-- 退回 ------+-> 新返工轮次 -> 数据处理
```

每个阶段展示：

- 阶段名称和状态：待处理、进行中、已完成、需返工。
- 责任角色。
- 数量摘要，例如已提交、已确认、已验收数量。
- 阶段完成条件。
- 当前阶段可用的主要操作入口。

`REWORK_REQUIRED` 必须显示退回来源和当前轮次；如果后端暂时不能提供退回来源，则统一显示“确认或验收退回”，不得伪造具体阶段。

`LEGACY_PROGRESS` 不展示闭环步骤，改为明确的历史任务提示，只展示历史完成量、计划记录和只读原因。

### 4.5 页面层级

任务详情按以下顺序组织：

1. 任务名称、状态、负责人、截止日期和当前轮次。
2. 闭环流程步骤或历史任务提示。
3. 计划工作区：甘特图或表格。
4. 自动阶段进度和风险摘要。
5. 治理范围、规则快照和问题集合。

默认视图规则：

- `DRAFT` 默认表格，保持计划编排效率。
- `IN_PROGRESS` 及后续闭环状态默认甘特图。
- 历史任务默认甘特图，但只展示历史计划，不展示闭环里程碑。
- 用户在当前页面切换视图后保持选择，编辑计划时自动回到表格。

范围和规则快照使用业务摘要展示，原始 JSON 放入可展开的技术详情。空问题集合不占用大块固定高度。

### 4.6 异常处理

- 计划投影失败时显示加载错误，不回退到可能过期的存储完成量。
- 不存在的依赖不绘制连线，并在计划行标识依赖数据异常。
- 历史任务没有范围快照时显示“历史任务未固化范围快照”，不显示空 JSON。
- 闭环任务缺少范围或规则快照时显示阻断错误，不能伪装为正常流程。
- 返工来源不可确定时使用中性文案，不根据状态猜测。

### 4.7 第一期验收标准

| 编号 | 验收内容 |
| --- | --- |
| P1-AC-01 | 任务 1 的两条依赖箭头均从前置计划指向后续计划，终段向右 |
| P1-AC-02 | 任务 4 的甘特计划状态和完成量与任务详情聚合结果一致 |
| P1-AC-03 | `LEGACY_PROGRESS` 页面不展示业务确认、质量验收和正式应用闭环步骤 |
| P1-AC-04 | `CLOSED_LOOP_V1` 页面展示六阶段连接流程及当前阶段 |
| P1-AC-05 | 确认或验收退回后明确显示返工轮次和返回数据处理的方向 |
| P1-AC-06 | 草稿默认表格，执行中及后续闭环任务默认甘特图 |
| P1-AC-07 | 甘特进度只能来自治理项聚合，不能通过计划存储值覆盖 |
| P1-AC-08 | 1366×768 和 1920×1080 下核心流程与计划工作区可读，页面无整体横向溢出 |

## 5. 第二期：标准化与自动化治理

第二期拆成四个连续切片，每个切片单独设计、实施和验收。

### 5.1 切片 A：标准中心

- 维护数据标准、字段规则、命名规则、必填条件、文件角色、适用范围和质量门槛。
- 标准具有草稿、启用、停用状态以及不可覆盖的版本。
- 展示负责人、生效时间、变更说明和潜在影响资产数量。
- 任务启动时冻结标准、字典和质量策略版本。
- 新标准启用后生成受影响资产复核清单，不改变执行中任务。

实施状态：已完成。后端提供内存/JDBC 双适配器、不可覆盖版本状态机、启停并发校验、影响资产 ID 清单和任务启动标准版本校验；前端提供标准版本工作台、规则维护、启停确认和影响复核视图。

### 5.2 切片 B：映射规则

- 管理来源维度、来源值、目标字典项和完整 `AssetScope`。
- 支持待确认、已确认、已停用状态及版本历史。
- 显示确认人、使用次数、命中数量和潜在影响。
- 已确认且无歧义的规则可自动建议；歧义规则必须逐项业务确认。
- 产品条件和生产条件必须在同一 `AssetScope` 内匹配。

实施状态：已完成。后端提供映射规则内存/JDBC 双适配器、状态与规则版本历史、目标字典启用校验、完整范围一致性校验、歧义确认意见校验和乐观锁；前端提供映射规则列表、详情、版本新增、确认/停用和“可自动建议”标识。本切片只沉淀规则，不自动写入资产；自动扫描和批量建议属于切片 C。

### 5.3 切片 C：自动问题扫描

- 周期扫描缺失字段、非法字典值、重复记录、异常文件、失效责任人和标准变更影响。
- 问题按资产、问题类型、目标路径和规则版本生成稳定去重指纹。
- 相同问题不重复建单；已解决问题再次出现时重新打开并保留历史。
- 扫描只创建或更新问题，不直接覆盖正式数据。
- 支持人工触发、计划触发、运行记录、失败重试和影响数量。

实施状态：已完成。后端提供资产与规则检查、稳定问题指纹、重复运行幂等、已解决问题重开、扫描运行内存/JDBC 双适配器、人工触发/查询/失败重试 API 和默认关闭的固定间隔调度；前端提供自动扫描页、运行历史、统计指标、立即扫描、刷新和失败重试。扫描只创建或更新问题，不直接覆盖正式资产。

### 5.4 切片 D：治理运营

- 统一展示责任覆盖率、开放问题量、关闭周期、超期量、复发率和自动处理率。
- 展示一次确认通过率、验收通过率、返工率和正式应用成功率。
- 支持按标准、问题类型、责任人、资产类型、基地和时间筛选。
- 固化运营节奏：每日扫描、每周分派、每月质量复盘、季度标准评审。
- 指标用于发现风险和推动改进，不用于绕过业务确认或质量验收。

### 5.5 自动化分级

| 等级 | 系统行为 | 人工责任 |
| --- | --- | --- |
| L1 自动发现 | 识别问题并进入问题池 | 管理员确认优先级 |
| L2 自动建议 | 根据标准和已确认映射推荐结果 | 责任人确认歧义 |
| L3 受控批处理 | 对确定性规则批量生成拟变更结果 | 责任人处理例外 |
| L4 自动验收辅助 | 自动计算指标和固定抽样 | 内容管理员作验收决定 |
| L5 受控正式应用 | 验收通过后幂等写入并逐项重试 | 管理员处理不可恢复失败 |

自动化等级不代表可以取消责任人。任何涉及未知业务含义、范围歧义、拆分合并或高风险关系变化的操作都必须保留人工确认。

### 5.6 第二期总体验收标准

- 每项启用标准具有责任人、版本、生效范围和变更说明。
- 标准和映射变化可以计算影响范围并生成复核问题。
- 自动扫描可重复运行，不重复创建同一规则版本的问题。
- 自动建议保留命中的标准、字典和映射版本。
- 治理运营指标可追溯到任务、治理项和审计事件。
- 新数据入口执行当前启用标准，存量数据通过扫描进入治理队列。
- 自动化失败不会覆盖原值或丢失已经成功的治理项。

## 6. 交付顺序

```text
第一期：闭环可信度修复
  -> A 标准中心
  -> B 映射规则
  -> C 自动问题扫描
  -> D 治理运营
```

标准中心先于映射和扫描，因为自动化必须引用稳定、可版本化的标准。映射规则先于自动扫描的批量建议，因为系统需要明确哪些旧值转换已经获得业务确认。治理运营最后汇总前述能力产生的真实数据。

## 7. 测试策略

第一期必须覆盖：

- 后端计划投影契约测试，验证任务详情和计划接口结果一致。
- 依赖路径纯函数测试，验证正常、相邻、重叠和反向排期的终段方向。
- 工作流版本与任务状态的流程模型测试。
- 任务详情组件测试，覆盖默认视图、历史提示、返工和错误状态。
- 1366×768、1920×1080 浏览器验收，检查箭头、流程、首屏层级和横向溢出。

第二期各切片必须分别覆盖领域规则、版本不可覆盖、并发冲突、权限、影响范围、幂等执行和审计完整性。自动扫描另需覆盖重复运行、部分失败和恢复。

## 8. 非目标

- 不建设通用项目管理、资源负荷、成本核算或跨项目关键路径。
- 不把业务确认扩展为工程审批或生产放行。
- 不允许执行中通过甘特图拖拽修改锁定计划。
- 不允许自动规则填入无法确认的业务信息。
- 不在一个版本中同时交付第二期全部四个切片。

## 9. 完成定义

第一期只有在所有 P1 验收标准通过、前后端计划事实统一、历史任务语义隔离、流程步骤可理解且浏览器证据完整后才算完成。

第二期每个切片独立完成规格、实现、验证和上线准备；四个切片完成后，平台才从“字段治理闭环”升级为“可常态运营的数据治理平台”。
