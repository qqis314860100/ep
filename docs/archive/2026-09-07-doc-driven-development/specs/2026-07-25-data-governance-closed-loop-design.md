# 数据治理闭环设计

## 目标

将当前“治理任务编排与手工进度”升级为完整的数据治理作业平台。所有治理动作在系统内完成，实际处理结果依次经过业务确认和质量验收，验收通过后才成为资产正式标准值；退回结果进入可追踪的返工轮次。

最终支持以下治理动作：

- 字段补充与规范化。
- 旧值到标准值的映射。
- 文件角色和文件归组调整。
- 资产拆分与合并。
- 重复资产处理。
- 异常文件处理。
- 标准变更后的持续复核。

本设计不把系统扩展为通用项目管理工具，不包含工程审批、生产批准或自动生成未知业务含义。

## 当前基线

当前代码已经具备：

- 治理任务创建、查询和负责人选择。
- 草稿阶段的计划项新增、责任人、起止日期、计划数量和前置依赖。
- 任务启动后计划结构锁定。
- 计划状态、甘特图、责任分布和任务完成量更新。
- `governance_task`、`governance_plan` 本地表和基础接口测试。

当前能力停留在任务管理层：完成量由用户手工填写，任务到达 `PENDING_CONFIRMATION` 后没有确认、验收和标准化接口；清洗结果、原值/新值、确认记录、质量指标和返工轮次均未建模。

## 设计原则

1. **结果驱动进度**：任务和计划进度从治理项状态聚合，不再允许独立手工填写完成数量。
2. **先暂存、后生效**：执行阶段保存拟变更结果，业务确认和质量验收通过后才写入正式扩展数据。
3. **原始事实不可覆盖**：旧主键、旧来源字段和旧文件关联始终保留；标准值写入扩展结构。
4. **范围不可漂移**：任务启动时固化治理范围、问题集合和规则版本；新增问题进入其他任务。
5. **计划结构锁定**：开始执行后冻结计划项、责任人、排期和依赖，只允许更新执行结果。
6. **退回形成轮次**：确认或验收退回进入“待返工”，保留上一轮结果和意见，不覆盖历史。
7. **同一范围匹配**：产品和生产条件必须在同一个 `AssetScope` 中满足，禁止跨范围拼接。
8. **批量操作可恢复**：每条治理项独立返回结果；局部失败不丢失已成功项，并允许幂等重试。
9. **默认环境安全**：保持默认内存后端，不连接或修改生产数据库；正式写入仅通过受控扩展表迁移启用。

## 交付策略

采用纵向闭环、分切片交付，最终全部在系统内完成：

1. 字段补充闭环。
2. 映射规则闭环。
3. 文件归组和异常文件闭环。
4. 拆分、合并和重复处理闭环。
5. 持续治理、风险看板和治理报告。

第一切片建立所有后续动作复用的状态机、治理项、结果版本、确认、验收、审计和自动进度能力。后续切片只扩展动作处理器、结果结构和专属校验。

## 生命周期

### 资产生命周期

资产生命周期保持为：

```text
草稿 -> 待整理 -> 已标准化 -> 已停用
```

治理任务启动不改变资产状态。任务完成也不必然使任务内全部资产标准化：只有某资产满足当前启用标准、没有未解决的阻断问题，并通过业务确认和质量验收时，才从“待整理”进入“已标准化”。

### 治理任务状态

```text
DRAFT
  -> IN_PROGRESS
  -> PENDING_CONFIRMATION
  -> PENDING_ACCEPTANCE
  -> COMPLETED

PENDING_CONFIRMATION -> REWORK_REQUIRED -> IN_PROGRESS
PENDING_ACCEPTANCE   -> REWORK_REQUIRED -> IN_PROGRESS
```

状态含义：

| 状态 | 含义 | 允许操作 |
| --- | --- | --- |
| `DRAFT` | 范围和计划尚可编排 | 修改范围、计划、责任人和排期 |
| `IN_PROGRESS` | 执行人处理治理项 | 保存结果草稿、批量处理、提交结果 |
| `PENDING_CONFIRMATION` | 等待资产责任人确认业务含义 | 保存确认决定、完成确认轮次 |
| `PENDING_ACCEPTANCE` | 等待内容管理员质量验收 | 计算指标、抽样、通过或退回 |
| `REWORK_REQUIRED` | 存在确认或验收退回项 | 查看退回原因、开启新返工轮次 |
| `COMPLETED` | 验收通过且正式结果应用完成 | 只读查看报告和审计历史 |

不在首期增加取消、暂停和执行中改计划。后续如增加，必须记录原因和操作人，不能绕过计划锁定。

### 治理计划状态

计划状态为 `NOT_STARTED`、`IN_PROGRESS`、`BLOCKED`、`DONE`。

- 前置计划未完成时计划为 `BLOCKED`，后端拒绝开始该计划。
- 计划完成量由关联治理项聚合。
- 只有计划内全部治理项均已提交或进入更后阶段时，计划才能变为 `DONE`。
- 计划状态不能直接把全部计划数量标记为完成。

### 治理项状态

治理项是最小可处理、可确认、可验收单元，例如“资产 1024 的基地缺失”。

```text
PENDING -> PROCESSING -> SUBMITTED -> CONFIRMED -> ACCEPTED
                         |             |
                         +-> REWORK_REQUIRED <-+
```

无法确认的信息标记为 `BLOCKED` 并记录原因，不得填入假数据，不计入完成量，也不能通过阶段门禁。

## 核心领域对象

### 治理任务 `GovernanceTask`

- 稳定任务 ID 和任务编号。
- 名称、治理动作类型、问题类型、负责人和计划完成日期。
- 状态、当前治理轮次、工作流版本和乐观锁版本。
- 范围快照 ID、质量策略快照 ID。
- 执行、确认、验收和正式应用摘要。

### 范围快照 `GovernanceScopeSnapshot`

- 创建任务时使用的筛选条件。
- 启动任务时固化的资产 ID、问题 ID 和规则版本。
- 创建人、创建时间和治理项数量。
- 启动后不可修改。

范围快照防止任务执行期间因搜索条件或资产变化导致任务总量漂移。资产新出现的问题进入持续治理队列或新任务。

### 治理计划 `GovernancePlan`

- 计划名称、顺序、责任人、起止日期。
- 数量单位、前置计划和状态。
- 与治理项的一对多关联。
- 完成量由治理项聚合，不保存可独立修改的业务完成量。

保存计划依赖时必须校验依赖计划属于同一任务、不能依赖自身且不能形成环。任务启动时再次校验完整依赖图。

### 数据标准 `DataStandard`

- 标准名称、适用资产类型、责任人、状态和生效时间。
- 不可覆盖的标准版本及变更说明。
- 必填字段、字段类型、字典约束、`AssetScope` 约束、命名和文件角色规则。
- 状态：`DRAFT`、`ENABLED`、`DISABLED`。

治理任务引用启动时的标准版本快照。启用新版本不会改变执行中的任务，只生成受影响资产复核问题。

### 映射规则 `GovernanceMappingRule`

- 来源维度、来源值、目标字典项和适用 `AssetScope`。
- 确认人、状态、版本和使用次数。
- 状态：`PENDING_CONFIRMATION`、`CONFIRMED`、`DISABLED`。

映射规则只能在完整适用范围内匹配。来源文本相同但范围不同的规则是不同规则，不能跨范围合并命中。

### 资产责任 `AssetResponsibility`

- 资产、责任人、业务确认人、责任范围和状态。
- 分配、认领、移交的操作人、时间和原因。
- 人员失效时生成持续治理问题，不静默改派。

### 质量策略 `GovernanceQualityPolicy`

- 策略名称、适用治理动作和资产类型。
- 启用的指标、阈值、阻断规则和抽样规则。
- 状态、版本、生效时间和责任人。

任务启动时生成不可变质量策略快照，保证同一治理批次使用一致验收口径。

### 治理问题 `GovernanceIssue`

- 资产 ID、问题类型、目标类型和目标路径。
- 检测规则与规则版本。
- 原始事实快照、严重程度和阻断标记。
- 状态：开放、已纳入任务、已解决、重新打开。
- 去重指纹：资产、问题类型、目标路径和规则版本的组合。

### 治理项 `GovernanceItem`

- 任务、计划和治理问题 ID。
- 资产 ID、动作类型、责任人和状态。
- 原始版本、当前结果版本和治理轮次。
- 阻塞原因、退回来源和乐观锁版本。

### 结果版本 `GovernanceResultVersion`

- 治理项、治理轮次和版本号。
- 操作类型、原值 JSON、拟变更值 JSON。
- 使用的标准、字典和映射规则版本。
- 处理人、处理时间和提交时间。
- 状态：`DRAFT`、`SUBMITTED`、`SUPERSEDED`、`APPLIED`。

上一轮结果被退回后保留为 `SUPERSEDED`，新轮次创建新结果版本，不覆盖旧结果。

### 业务确认轮次

`GovernanceConfirmationRound` 记录任务、治理轮次、确认人范围、开始和完成时间。`GovernanceConfirmationDecision` 逐项记录：

- 结果版本 ID。
- 确认人、决定和意见。
- `APPROVED` 或 `REJECTED`。
- 决定时间和版本。

允许分批保存决定；完成轮次时必须覆盖全部已提交治理项。存在拒绝项则任务进入 `REWORK_REQUIRED`，否则进入 `PENDING_ACCEPTANCE`。

### 质量验收轮次

`GovernanceAcceptanceRound` 记录任务、治理轮次、质量策略快照、指标结果、抽样集合和最终结论。

- 指标结果保存计算分子、分母、结果值、阈值和是否通过。
- 抽样记录保存资产、治理项、检查人、结果和问题说明。
- 退回必须指定受影响治理项或由指标规则解析出的治理项集合。
- 存在退回项则进入 `REWORK_REQUIRED`；全部通过后触发正式结果应用。

### 审计事件

治理任务、计划、治理项、结果、确认、验收和正式应用的每次状态变化均写入 `GovernanceAuditEvent`。资产正式值变化同时写入现有资产审计扩展，不记录文件内容、凭证或敏感请求头。

## 自动进度

系统分别展示三个进度，不使用容易误导的单一手工百分比：

- 执行进度：状态达到 `SUBMITTED` 及之后的治理项数 / 当前轮次全部治理项数。
- 确认覆盖率：已有确认决定的治理项数 / 当前轮次已提交治理项数。
- 确认通过率：确认通过治理项数 / 已决定治理项数。
- 验收覆盖率：已有验收结果的治理项数 / 已确认治理项数。
- 验收通过率：验收通过治理项数 / 已验收治理项数。

`BLOCKED` 和 `REWORK_REQUIRED` 保留在分母中并单独展示。计划进度按计划关联治理项聚合，任务列表展示当前阶段、执行进度、风险数量和截止日期。

## 第一切片：字段补充闭环

### 问题发现与建单

内容管理员从问题池筛选缺少基地、拉线、专业类别、功能说明或负责人的资产。创建任务时系统生成治理问题和治理项草稿；任务启动时固化资产、字段、原值、当前资产版本、标准版本和 `AssetScope`。

同一资产可以有多个字段治理项。任务总量以治理项计数，而不是简单资产数。

### 清洗工作台

工作台分为：

- 左侧治理项队列：待处理、处理中、阻塞、待返工和已提交。
- 中间原值与拟变更值：展示资产、问题、原始事实和字段编辑器。
- 右侧规则上下文：启用标准、字典、映射候选、历史结果和退回意见。

系统支持逐项保存结果草稿和受控批量处理。批量处理只允许同一问题类型、同一标准版本且匹配同一 `AssetScope` 的治理项；歧义映射必须逐项确认。

提交时校验资产原始版本。资产已经被其他用户修改时，该治理项返回 `409 Conflict` 并要求刷新，不影响批次内其他成功项。

### 业务确认

资产责任人只看到已提交结果，同时查看原值、拟变更值、规则来源和执行人。确认支持逐项保存、批量通过和逐项退回；退回必须填写意见。

批量通过只适用于同一结果类型和同一责任范围，不允许跨资产权限批量确认。

### 质量验收

首期指标包括：

- 必填字段完整率。
- `AssetScope` 层级合法率。
- 标准字典命中率。
- 负责人覆盖率。
- 抽样准确率。

指标公式、阈值和适用资产类型在任务启动时形成质量策略快照。标准在执行中发生变化时不影响当前任务，变更后的影响资产进入复核队列。

统一计算口径：

- 必填字段完整率 = 已填写且通过类型校验的必填字段数 / 应检查必填字段数。
- `AssetScope` 层级合法率 = 通过平台、蓝本、基地、拉线和工序段层级校验的范围数 / 应检查范围数。
- 标准字典命中率 = 绑定当前任务标准版本允许字典项的字段数 / 应使用字典的字段数。
- 负责人覆盖率 = 存在有效资产责任关系的资产数 / 当前治理资产数。
- 抽样准确率 = 抽样检查通过的治理项数 / 实际抽样治理项数。

分母为零的指标标记为“不适用”，不自动按 100% 处理；质量策略必须明确“不适用”是否允许通过。抽样集合由后端按策略生成并保存，验收人员不能只删除失败样本后重新计算。

### 正式生效

验收通过后，系统启动幂等正式应用作业：

1. 再次校验资产版本和结果版本。
2. 将拟变更值写入资产扩展数据，不修改旧来源字段。
3. 标记结果版本为 `APPLIED`。
4. 重新运行资产完整性与标准化判断。
5. 符合全部启用标准且没有开放阻断问题的资产进入“已标准化”。
6. 其他资产保持“待整理”，但当前治理项可以视为完成。
7. 全部结果应用完成后任务进入 `COMPLETED` 并生成治理报告。

正式应用采用逐项幂等处理和作业进度，不使用覆盖整个大批次的长事务。失败项保留错误原因并可重试；任务在全部应用成功前保持“待质量验收”，页面显示“验收通过，正在归档”的子状态。

## 后续治理动作

### 映射规则闭环

- 聚合旧平台、旧拉线和旧分类值及其出现次数。
- 映射规则包含来源维度、来源值、目标值、适用 `AssetScope`、确认人、状态和版本。
- 映射状态为待确认、已确认和已停用。
- 旧拉线不能单独推断基地；多候选或跨范围情况生成歧义治理项。
- 批量应用生成结果版本，仍经过业务确认和质量验收。

### 文件归组与异常文件闭环

- 展示原文件关联、文件角色、主文件、封面和拟归组结果。
- 同一资产包只能有一个主文件和一个封面预览文件。
- 文件内容摘要和实际类型参与重复与异常判断。
- 异常文件可标记为待替换、隔离或仅保留下载，不物理删除原文件。
- 文件结果验收后更新扩展关联并保留历史关联。

### 拆分闭环

- 用户逐个指定原文件、新资产包、适用范围和关系归属。
- 系统不得仅依据文件名自动拆分。
- 新资产先以待整理状态暂存，验收通过后正式建立去向关系。
- 原资产不物理删除，保留原编号、文件关联、收藏、评论和点赞，并提供新资产入口。

### 合并与重复处理闭环

- 必须指定保留的主资产。
- 逐项确认文件、适用范围、标签和关系如何处理。
- 编号冲突、文件重复和关系冲突未解决前不能提交确认。
- 被合并资产保留历史协作信息和到主资产的去向记录，不迁移或复制收藏、评论和点赞。

### 持续治理

- 新上传或修改资产按启用标准生成问题。
- 标准、字典或映射规则变更后生成受影响资产复核清单。
- 长期无人认领、异常文件、疑似重复和失效责任人持续进入问题池。
- 已标准化资产发现新的阻断问题时由内容管理员重新打开为“待整理”，并记录原因。

## 页面与导航

数据治理中心保留为“管理与治理”下的一级页面，内部采用稳定的工作视图，不新增通用项目导航。

### 治理总览

- 指标：开放问题、执行中任务、待确认、待验收、待返工、逾期和已标准化数量。
- 筛选：治理动作、问题类型、状态、负责人、截止日期和 `AssetScope`。
- 风险区：阻塞治理项、逾期计划、确认超时、验收不通过和正式应用失败。
- 任务表进入对应阶段工作台，不在总览中展开大型表单。

### 问题池

- 按问题类型、严重程度、资产状态、旧值和范围筛选。
- 支持选择问题创建治理任务并预览范围快照。
- 同一问题已被活动任务占用时不能重复纳入。

### 任务详情

- 概览：阶段、三个进度、负责人、截止日期和风险。
- 计划：仅草稿可编辑，执行后只读展示甘特和依赖。
- 治理项：按当前阶段跳转清洗、确认、验收或返工视图。
- 历史：按轮次展示结果、确认、验收、正式应用和审计事件。

### 专用工作台

- 清洗工作台面向执行负责人。
- 业务确认队列面向资产责任人。
- 质量验收台面向内容管理员。
- 拆分与合并使用独立全页工作台，避免在抽屉中容纳复杂文件和关系操作。

## API 契约

API 使用明确业务命令，避免用通用状态字段绕过状态机。

### 问题与任务

- `GET /api/v1/governance/issues`：查询问题池。
- `POST /api/v1/governance/tasks`：按问题集合创建草稿任务。
- `GET /api/v1/governance/tasks`：按阶段、负责人、到期日和范围查询任务。
- `GET /api/v1/governance/tasks/{taskId}`：查询任务、进度和风险摘要。
- `POST /api/v1/governance/tasks/{taskId}/plans`：草稿阶段新增计划。
- `POST /api/v1/governance/tasks/{taskId}/start`：校验并启动任务、生成范围快照。
- `GET /api/v1/governance/tasks/{taskId}/items`：分页查询治理项。

### 执行

- `PUT /api/v1/governance/items/{itemId}/result-draft`：按预期版本保存结果草稿。
- `POST /api/v1/governance/items/{itemId}/submit`：提交单条结果。
- `POST /api/v1/governance/items/batch-results`：批量保存或提交同类结果。
- `POST /api/v1/governance/tasks/{taskId}/submit-for-confirmation`：校验所有治理项并进入待确认。

### 确认与验收

- `GET /api/v1/governance/tasks/{taskId}/confirmation-rounds/current`：查询当前确认轮次。
- `PUT /api/v1/governance/tasks/{taskId}/confirmation-rounds/{roundId}/decisions/{itemId}`：按轮次保存逐项确认决定。
- `POST /api/v1/governance/tasks/{taskId}/confirmation-rounds/{roundId}/complete`：完成指定确认轮次。
- `GET /api/v1/governance/tasks/{taskId}/acceptance-rounds/current`：查询指标和抽样集合。
- `PUT /api/v1/governance/tasks/{taskId}/acceptance-rounds/{roundId}/samples/{itemId}`：按轮次保存抽样结果。
- `POST /api/v1/governance/tasks/{taskId}/acceptance-rounds/{roundId}/complete`：通过或退回指定验收轮次。
- `POST /api/v1/governance/tasks/{taskId}/rework`：确认返工范围并开启新轮次。

### 审计与报告

- `GET /api/v1/governance/tasks/{taskId}/history`：查询各轮次历史。
- `GET /api/v1/governance/tasks/{taskId}/report`：查询治理报告。
- `GET /api/v1/governance/jobs/{jobId}`：查询批量处理或正式应用作业进度。

批量写入接受幂等键，返回每条治理项的成功、失败和冲突结果。资源不存在返回 `404`，参数错误返回 `400`，版本或状态冲突返回 `409`，无权限返回 `403`，只读环境写入返回明确的只读错误。

- `governance_item`
- `governance_result_version`
- `governance_confirmation_round`
- `governance_confirmation_decision`
- `governance_acceptance_round`
- `governance_acceptance_metric`
- `governance_acceptance_sample`
- `governance_quality_policy_snapshot`
- `governance_quality_policy`
- `data_standard`
- `data_standard_rule`
- `governance_mapping_rule`
- `governance_operation_job`
- `governance_audit_event`

所有表通过稳定 `drawing_id` 引用旧资产，不修改 `sys_drawing` 主键和来源字段。正式迁移使用新的版本化 DDL，不修改现有 V1.5 脚本。

现有任务增加 `workflow_version`：

- `LEGACY_PROGRESS`：没有治理项和结果版本的旧任务，只读展示原有进度，不伪造清洗结果。
- `CLOSED_LOOP_V1`：使用本设计的完整状态机。

本地种子任务可以重新生成闭环演示数据；生产历史任务必须通过只读盘点决定保留或人工重建，不能自动推断结果。

## 权限

| 操作 | 执行负责人 | 资产责任人 | 内容管理员 | 系统管理员 |
| --- | --- | --- | --- | --- |
| 查看授权治理项 | 是 | 负责资产 | 是 | 是 |
| 保存和提交清洗结果 | 分派范围 | 否 | 是 | 是 |
| 业务确认 | 否 | 负责资产 | 可协助但不可替代责任人 | 是 |
| 质量验收 | 否 | 否 | 是 | 是 |
| 管理标准和映射 | 否 | 否 | 是 | 是 |
| 开启返工 | 任务负责人 | 否 | 是 | 是 |
| 正式应用结果 | 否 | 否 | 由验收命令触发 | 是 |

所有查询和命令在后端校验角色、数据范围和资产范围，前端隐藏按钮不能代替权限校验。

## 错误、并发与恢复

- 治理项、任务、映射规则、确认决定和验收记录使用乐观锁。
- 批量命令逐项提交，返回成功、校验失败、版本冲突和无权限数量。
- 已提交结果不能原地修改；退回后创建新轮次和新结果版本。
- 正式应用作业逐项幂等，重复执行已应用结果不重复写入。
- 作业中断后从未完成项继续，不重放成功项。
- 规则、字典或资产版本冲突时停止受影响治理项，不静默选择新值。
- 前端保留筛选、当前治理项和未提交草稿；离开存在草稿时提示确认。
- 无权限响应不返回资产名称、编号、原值或文件信息。

## 后端模块边界

现有 `GovernanceTaskService` 拆分为职责明确的应用服务：

- `governance.task`：任务、计划、状态机和范围快照。
- `governance.issue`：问题检测、去重和问题池。
- `governance.execution`：治理项、结果版本和动作处理器。
- `governance.confirmation`：业务确认轮次和决定。
- `governance.acceptance`：质量策略、指标、抽样和正式应用。
- `governance.mapping`：映射规则及适用范围校验。
- `governance.audit`：治理审计和报告投影。

控制器只处理协议转换；应用服务编排事务；领域对象校验状态与不变量；仓储和正式资产写入通过基础设施端口实现。默认内存适配器和本地 JDBC 适配器遵守同一契约。

不同治理动作实现统一 `GovernanceActionHandler` 端口，负责结果结构校验、预览和正式应用。状态机、确认、验收和审计不依赖具体动作类型。

## 前端模块边界

将当前大型治理页面拆分为：

- `features/governance/overview`
- `features/governance/issues`
- `features/governance/tasks`
- `features/governance/execution`
- `features/governance/confirmation`
- `features/governance/acceptance`
- `features/governance/history`
- `services/governance/`

页面通过任务 ID、治理项 ID 和查询缓存协作，不共享页面级可变状态。清洗、确认、验收和复杂拆分合并使用独立路由；任务详情只承载摘要、计划、进度和入口。

- 覆盖全部合法和非法任务状态转换。

- 每个命令覆盖成功、参数错误、无权限、版本冲突和状态冲突。
- 批量接口验证逐项结果和幂等键。
- 历史和报告接口验证原值、新值、轮次和操作人完整。

- 默认内存仓储运行完整闭环测试。
- 本地 MySQL 验证任务、结果、确认、验收和正式应用的持久化。

- 治理项筛选、原值/新值编辑、批量结果和冲突恢复。

## 切片验收

### 切片 1：字段补充

- 从问题池创建任务并固化范围。
- 处理字段、查看原值/新值并自动形成进度。
- 完成业务确认、质量验收、返工和再次验收。
- 验收后正式写入扩展数据并正确判断资产状态。

### 切片 2：映射规则

- 建立、确认、停用映射并显示适用范围。
- 歧义映射不能自动应用。
- 已确认映射批量应用后经过同一确认和验收闭环。

### 切片 3：文件治理

- 文件角色、主文件和文件归组可在系统内处理。
- 异常文件保留原始事实和处理结论。
- 部分失败不影响其他治理项，并可重试。

### 切片 4：复杂资产治理

- 拆分和合并逐项指定文件、范围和关系归属。
- 原资产、编号、文件关联和协作历史可追溯。
- 冲突未解决时不能进入确认。

### 切片 5：持续治理

- 新问题和标准变更影响资产进入问题池。
- 风险看板展示阻塞、逾期、待确认、待验收和返工。
- 可查询每个任务的治理报告和完整审计历史。

## 完成定义

数据治理闭环完成必须同时满足：

- 所有治理动作均产生结构化治理项和结果版本。
- 任务、计划和总览进度完全由治理项聚合。
- 业务确认、质量验收、返工和正式应用均有真实接口与持久化记录。
- 验收通过前拟变更值不会成为资产正式标准值。
- 旧来源值、旧主键和历史协作信息不被覆盖或物理删除。
- 所有状态、权限、并发、批量失败和恢复规则有自动化测试。
- 默认开发配置不连接生产数据库。
